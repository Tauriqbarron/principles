Normal Forms
Normalisation

Normalisation is the systematic process of organising data to eliminate redundancy and prevent update anomalies. Each normal form builds on the previous one, enforcing stricter rules about how data depends on keys.

Sources: C.J. Date — An Introduction to Database Systems · Hernandez — Database Design for Mere Mortals

1NF

Every column holds atomic (indivisible) values. No repeating groups or arrays inside a single cell.
One value, one cell. No comma-separated lists.

2NF

Every non-key column must depend on the entire primary key, not just part of it.
Eliminate partial dependencies on composite keys.

3NF

Non-key columns must depend on the key directly — not through another non-key column.
No transitive dependencies. Every column tells you about the key, the whole key, and nothing but the key.

BCNF

Every determinant must be a candidate key. Stricter than 3NF — handles edge cases where a non-candidate-key column determines part of a key.
If X → Y, then X must be a superkey.
1
First Normal Form
Atomic values — no comma-separated lists.

Storing multiple values in a single column makes querying, filtering, and joining almost impossible without string manipulation hacks.

Before — 1NF Violation schema.sql 
-- ❌ Skills stored as a comma-separated string.
-- How do you find all employees who know C#?
-- LIKE '%C#%' is fragile and un-indexable.

CREATE TABLE Employees (
    Id         INT PRIMARY KEY,
    Name       NVARCHAR(100),
    Skills     NVARCHAR(MAX)
    -- 'C#, SQL, Docker, React'
);

-- Painful query:
SELECT * FROM Employees
WHERE Skills LIKE '%C#%';
-- Also matches 'C#Sharp', 'AC#E' etc.
After — 1NF Compliant schema.sql 
-- ✓ Junction table: each skill is its
-- own row. Clean, indexable, joinable.

CREATE TABLE Employees (
    Id    INT PRIMARY KEY,
    Name  NVARCHAR(100)
);

CREATE TABLE EmployeeSkills (
    EmployeeId  INT REFERENCES Employees(Id),
    Skill       NVARCHAR(50),
    PRIMARY KEY (EmployeeId, Skill)
);

-- Clean query:
SELECT e.* FROM Employees e
JOIN EmployeeSkills es
  ON e.Id = es.EmployeeId
WHERE es.Skill = 'C#';
⚠ The Jaywalking antipattern: Comma-separated lists in a single column break querying, indexing, referential integrity, and make aggregation impossible. Bill Karwin calls this the most common database antipattern.
✓ The fix: Create an intersection (junction) table. Each value gets its own row. You gain indexing, foreign keys, and clean JOIN queries. This is the foundational rule of 1NF.
3
Third Normal Form
Eliminate transitive dependencies.

When a non-key column determines another non-key column, you get update anomalies: change a city's region and you have to update every row that mentions that city.

Before — 3NF Violation orders.sql 
-- ❌ Region depends on City, not on OrderId.
-- Change Auckland's region? Update every
-- order row from Auckland.

CREATE TABLE Orders (
    OrderId      INT PRIMARY KEY,
    CustomerId   INT,
    City         NVARCHAR(50),
    Region       NVARCHAR(50)
    -- City → Region (transitive!)
);

-- Auckland, Auckland Region
-- Wellington, Wellington Region
-- Christchurch, Canterbury
-- Auckland, Auckland Region  (duplicated)
After — 3NF Compliant orders.sql 
-- ✓ Cities table owns the City → Region
-- relationship. Orders just references City.

CREATE TABLE Cities (
    CityName  NVARCHAR(50) PRIMARY KEY,
    Region    NVARCHAR(50) NOT NULL
);

CREATE TABLE Orders (
    OrderId     INT PRIMARY KEY,
    CustomerId  INT,
    City        NVARCHAR(50)
      REFERENCES Cities(CityName)
);

-- Region lives in ONE place.
-- Update it once, it's correct everywhere.
✓ The mantra: "Every non-key column must provide a fact about the key, the whole key, and nothing but the key — so help me Codd." This phrase encapsulates 1NF through 3NF in a single sentence.

Transaction Guarantees
ACID Properties

ACID describes the four guarantees that database transactions must provide to ensure data remains correct even in the face of errors, crashes, and concurrent access. Understanding ACID deeply is essential for building applications that don't corrupt data.

Sources: Kleppmann — Designing Data-Intensive Applications · Silberschatz et al. — Database System Concepts

A — Atomicity

A transaction is all-or-nothing. If any part fails, the entire transaction is rolled back. You never get a half-completed transfer where money leaves one account but never arrives in another.

C — Consistency

A transaction moves the database from one valid state to another. All constraints, cascades, and triggers must be satisfied before a transaction can commit. This is the application's responsibility — the database just enforces the rules you've defined.

I — Isolation

Concurrent transactions behave as if they were executed sequentially. Different isolation levels (Read Committed, Repeatable Read, Serializable) trade strictness for performance. Phantom reads, dirty reads, and lost updates are the bugs that occur when isolation is too weak.

D — Durability

Once a transaction commits, the data survives any subsequent crash — power failure, hardware fault, anything. Implemented through write-ahead logs (WAL) and flushing to disk before acknowledging the commit.

A
Atomicity in Practice
Wrap related operations in a transaction.

Without explicit transactions, each statement auto-commits independently. If the second statement fails, the first has already committed — leaving your data in an inconsistent state.

Before — No Transaction transfer.sql 
-- ❌ Each statement auto-commits.
-- If the second UPDATE fails, money
-- has vanished into thin air.

UPDATE Accounts
SET Balance = Balance - 500
WHERE AccountId = 1;

-- 💥 Server crashes here!

UPDATE Accounts
SET Balance = Balance + 500
WHERE AccountId = 2;

-- Account 1 lost $500.
-- Account 2 never received it.
After — Explicit Transaction transfer.sql 
-- ✓ Both statements succeed together
-- or fail together. No half-states.

BEGIN TRANSACTION;

UPDATE Accounts
SET Balance = Balance - 500
WHERE AccountId = 1;

UPDATE Accounts
SET Balance = Balance + 500
WHERE AccountId = 2;

COMMIT;

-- If anything fails, both are
-- rolled back automatically.
✓ In application code: In .NET, use TransactionScope or IDbTransaction. In Entity Framework, SaveChanges() wraps all pending changes in a single transaction by default. Always keep transactions short to avoid blocking other queries.
I
Isolation Levels
Understand the concurrency bugs each level prevents.

Read Uncommitted

Can see uncommitted changes from other transactions (dirty reads). Rarely used — almost never what you want.

Read Committed

The default in PostgreSQL and SQL Server. You only see committed data, but the same query within a transaction can return different results if another transaction commits in between (non-repeatable reads).

Repeatable Read

Once you read a row, it stays the same for the duration of your transaction. Prevents non-repeatable reads but can still see phantom rows (new rows inserted by other transactions).

Serializable

The strongest level. Transactions behave as if they ran one after another. Prevents all concurrency anomalies but at a performance cost. PostgreSQL implements this efficiently via SSI (Serializable Snapshot Isolation).

Performance Engineering
Indexing & Query Performance

An unindexed query on a million-row table scans every single row. The right index turns that full table scan into a near-instant lookup. But indexes aren't free — they consume disk space and slow down writes. Understanding when and how to index is one of the highest-leverage skills in database work.

Sources: Karwin — SQL Antipatterns · Kleppmann — DDIA · Markus Winand — SQL Performance Explained

B-Tree Index

The default index type. Keeps data sorted in a balanced tree structure. Excellent for equality checks (=), range queries (BETWEEN), and ordering (ORDER BY). Used by almost every relational database by default.

Hash Index

Optimised for exact equality lookups only. O(1) average lookup time. Cannot be used for range queries or sorting. Good for lookup tables and join keys when you only ever query with =.

Composite Index

An index on multiple columns — order matters. An index on (LastName, FirstName) helps queries filtering on LastName alone, or on both, but not on FirstName alone. The leftmost prefix rule.

Covering Index

When an index includes all the columns a query needs, the database can answer the query entirely from the index without touching the table. Look for "Index Only Scan" in your query plan.

!
Antipattern: Index Shotgun
Not too few, not too many — just the right indexes.

The Index Shotgun antipattern comes in two flavours: creating no indexes at all (every query is a full table scan), or creating an index on every column (writes become glacially slow and storage balloons).

Problem — No Indexes query-plan.sql 
-- ❌ 2.3 million rows, no index on Email.
-- Full table scan every single time.

SELECT * FROM Users
WHERE Email = 'tauriq@example.com';

-- Execution plan shows:
-- Seq Scan on Users
-- cost=0.00..58293.00
-- rows=2,300,000 (ALL of them!)

-- Response time: 1,200ms
Fix — Targeted Index query-plan.sql 
-- ✓ Index on the column you actually
-- filter by. B-tree does the rest.

CREATE INDEX ix_users_email
ON Users (Email);

SELECT * FROM Users
WHERE Email = 'tauriq@example.com';

-- Execution plan shows:
-- Index Scan using ix_users_email
-- cost=0.43..8.45
-- rows=1

-- Response time: 0.3ms
⚠ The opposite extreme: Don't create an index on every column either. Each index must be maintained on every INSERT, UPDATE, and DELETE. A table with 15 indexes will have significantly slower writes. Profile your actual queries and index accordingly.
✓ How to decide: Use EXPLAIN ANALYZE (PostgreSQL) or look at the execution plan in SSMS (SQL Server). Index columns that appear in WHERE, JOIN, and ORDER BY clauses of your most frequent queries. Re-evaluate indexes periodically as query patterns change.
N
The N+1 Query Problem
One query to load parents, then N queries for children.

The N+1 problem is one of the most common performance killers in application code that uses an ORM. You load a list of records, then loop through each one and lazily load related data — firing a separate SQL query per row.

Before — N+1 Queries (C#) OrderService.cs 
// ❌ 1 query to load 200 orders,
// then 200 queries to load each customer.
// Total: 201 database round-trips.

var orders = db.Orders.ToList();

foreach (var order in orders)
{
    // Lazy load fires a query per order
    var name = order.Customer.Name;
    Console.WriteLine(
        $"{order.Id}: {name}");
}
After — Eager Load (C#) OrderService.cs 
// ✓ One query with a JOIN.
// Total: 1 database round-trip.

var orders = db.Orders
    .Include(o => o.Customer)
    .ToList();

foreach (var order in orders)
{
    // Already loaded — no extra query
    var name = order.Customer.Name;
    Console.WriteLine(
        $"{order.Id}: {name}");
}
✓ In Entity Framework: Use .Include() for eager loading. In Dapper, write an explicit JOIN. Always check your ORM's generated SQL — enable logging in development to catch N+1 patterns early.

Common Mistakes
SQL Antipatterns

Antipatterns are solutions that look reasonable on the surface but cause serious problems at scale. Bill Karwin's "SQL Antipatterns" catalogues the most common traps developers fall into — and the principled fixes. Knowing what not to do is as important as knowing best practices.

Source: Bill Karwin — SQL Antipatterns: Avoiding the Pitfalls of Database Programming
K
Keyless Entry
Skipping foreign keys "for flexibility" destroys data integrity.

Some developers avoid foreign keys because they think constraints slow things down or get in the way of agile development. The result: orphan rows, broken references, and bugs that only surface in production.

Before — No Foreign Keys schema.sql 
-- ❌ No FK constraint. Nothing stops you
-- from inserting an order for a customer
-- that doesn't exist.

CREATE TABLE Orders (
    Id          INT PRIMARY KEY,
    CustomerId  INT,
    Total       DECIMAL(10,2)
);

-- This succeeds silently:
INSERT INTO Orders (Id, CustomerId, Total)
VALUES (1, 99999, 250.00);
-- Customer 99999 doesn't exist.
-- Now your reports are wrong.
After — Enforced Foreign Key schema.sql 
-- ✓ The database enforces the relationship.
-- You can't insert garbage references.

CREATE TABLE Orders (
    Id          INT PRIMARY KEY,
    CustomerId  INT NOT NULL,
    Total       DECIMAL(10,2),
    CONSTRAINT FK_Orders_Customer
      FOREIGN KEY (CustomerId)
      REFERENCES Customers(Id)
);

-- This now fails with an error:
-- "INSERT conflicts with FOREIGN KEY
--  constraint FK_Orders_Customer"
✓ The principle: Let the database enforce data integrity, not your application code. Application bugs come and go, but foreign keys are enforced at every entry point — raw SQL, ORM, migration scripts, manual data fixes. Constraints are your last line of defence.
?
Fear of the Unknown
Misusing NULL — or avoiding it by inventing magic values.

NULL means "unknown" — not zero, not empty string, not "N/A". Using magic sentinel values like -1 or "NONE" instead of NULL creates bugs that are even harder to find. But NULLs have their own traps in comparisons and aggregations.

Problem — Magic Values users.sql 
-- ❌ Using -1 to mean "no phone number".
-- Every query must know about this
-- magic value, or the report is wrong.

CREATE TABLE Users (
    Id     INT PRIMARY KEY,
    Name   NVARCHAR(100),
    Phone  NVARCHAR(20)
      DEFAULT 'UNKNOWN'
);

-- How many users have a phone?
SELECT COUNT(*) FROM Users
WHERE Phone != 'UNKNOWN'
  AND Phone != 'N/A'
  AND Phone != '';
-- What other magic values did someone
-- invent? We'll never catch them all.
Fix — Use NULL Correctly users.sql 
-- ✓ NULL means "we don't know".
-- SQL has built-in syntax for this.

CREATE TABLE Users (
    Id     INT PRIMARY KEY,
    Name   NVARCHAR(100),
    Phone  NVARCHAR(20) -- nullable
);

-- How many users have a phone?
SELECT COUNT(*) FROM Users
WHERE Phone IS NOT NULL;

-- Clean. Unambiguous.
-- COUNT(), SUM(), AVG() all handle
-- NULLs correctly by design.

-- But remember: NULL != NULL.
-- Use IS NULL, never = NULL.
⚠ The trap: WHERE Phone = NULL returns no rows — not because there aren't any, but because NULL = NULL evaluates to NULL (unknown), which is not TRUE. This is three-valued logic and it catches everyone at least once.
E
Entity-Attribute-Value (EAV)
The "infinitely flexible" schema that's infinitely painful.

EAV stores data as key-value pairs instead of typed columns. It seems flexible — "we can add any attribute without a migration!" — but you lose type safety, constraints, and joins become monstrous pivot queries.

Problem — EAV Table products.sql 
-- ❌ Everything is a string.
-- No type checking, no constraints,
-- querying is a nightmare.

CREATE TABLE ProductAttributes (
    ProductId  INT,
    AttrName   NVARCHAR(50),
    AttrValue  NVARCHAR(MAX)
);

-- "Give me all products where
--  weight < 5kg AND colour = 'red'"
SELECT p.ProductId
FROM ProductAttributes p
JOIN ProductAttributes w
  ON p.ProductId = w.ProductId
WHERE p.AttrName = 'colour'
  AND p.AttrValue = 'red'
  AND w.AttrName = 'weight'
  AND CAST(w.AttrValue AS DECIMAL) < 5;
-- Self-join per attribute. Grows O(n).
Fix — Typed Columns (or JSONB) products.sql 
-- ✓ Option A: Real columns with types.

CREATE TABLE Products (
    Id      INT PRIMARY KEY,
    Name    NVARCHAR(100),
    Colour  NVARCHAR(30),
    Weight  DECIMAL(6,2)
);

SELECT * FROM Products
WHERE Colour = 'red'
  AND Weight < 5;
-- Simple, fast, type-safe.

-- ✓ Option B: JSONB for truly dynamic
-- attributes (PostgreSQL):
-- attrs JSONB, with a GIN index.
-- Flexible AND queryable.
✓ When EAV is legitimate: When you genuinely have thousands of possible attributes that vary per entity (e.g. medical record systems, product catalogues with wildly different categories). Even then, consider a hybrid: core columns for common attributes + JSON/JSONB for the rest.

System Design
Data-Intensive Application Principles

Martin Kleppmann's "Designing Data-Intensive Applications" is widely considered the most important book on modern data systems. These are the core principles it establishes — the lens through which every data design decision should be evaluated.

Source: Martin Kleppmann — Designing Data-Intensive Applications (O'Reilly, 2017; 2nd ed. 2026)

Reliability

The system works correctly even when things go wrong — hardware faults, software bugs, human errors. Fault-tolerant systems anticipate faults and handle them gracefully, rather than hoping they won't happen. Design for failure, not for the happy path.

Scalability

As load increases, the system can cope without degrading. Scalability isn't a binary — you describe it in terms of specific load parameters (requests/sec, read/write ratio, data volume) and how performance changes as those parameters grow.

Maintainability

The majority of software cost is ongoing maintenance, not initial development. Maintainable systems are operable (easy to run), simple (easy to understand), and evolvable (easy to change). This is the principle that matters most over a system's lifetime.

D
Data Model Trade-offs
Choose the model that fits your access patterns.

Relational, document, graph — each data model makes certain operations easy and others awkward. The model you choose shapes how you think about the problem and determines which queries are natural vs. painful.

Relational (SQL)

Best when data has many relationships, you need strong consistency, and your queries involve complex joins. Normalised data means no redundancy, and schemas enforce structure at write time (schema-on-write).

Document (NoSQL)

Best for data that comes in self-contained "documents" — user profiles, blog posts, product listings. Flexible schema (schema-on-read), great locality (one read to fetch everything). Poor for many-to-many relationships.

Graph

Best when the connections between entities are the data — social networks, recommendation engines, fraud detection. Excels at traversing relationships that would require recursive joins in SQL.

R
Replication & Partitioning
The fundamental trade-offs of distributed data.

Replication keeps copies of data on multiple machines for fault tolerance. Partitioning (sharding) splits data across machines for scalability. Both introduce complexity around consistency, conflict resolution, and operational overhead.

Single-Leader Replication

One node handles writes, replicas handle reads. Simple model with clear consistency. Used by PostgreSQL, MySQL, SQL Server. Risk: leader failure requires failover.

Multi-Leader Replication

Multiple nodes accept writes — useful for multi-datacentre setups. But now you need conflict resolution: what happens when two leaders modify the same row simultaneously?

Leaderless Replication

Any node accepts reads and writes (e.g. Cassandra, DynamoDB). Uses quorum reads/writes. Eventual consistency means stale data is possible.

✓ The key insight from DDIA: There is no "best" replication strategy. Each is a set of trade-offs between consistency, availability, latency, and operational complexity. Understand your application's requirements — does it need strong consistency (banking)? Or is eventual consistency acceptable (social media feeds)?

Guiding Principles
Database Design Philosophy

Beyond specific techniques, these are the overarching philosophies that guide good database design. They emerge from decades of practice across relational databases, distributed systems, and real-world production failures.

Synthesised from: C.J. Date · Bill Karwin · Martin Kleppmann · Ralph Kimball · Michael Hernandez
1
Data Outlives Code
Your application will be rewritten. Your data will not.

Applications get rewritten every 5–10 years. Data, once created, lives on decades. This means schema design deserves more care than any individual application feature. A bad schema creates pain that compounds over every future application that touches the data.

2
Constraints Are Features
Every constraint you omit is a bug you'll ship later.

NOT NULL, foreign keys, CHECK constraints, unique indexes — these aren't bureaucratic overhead. They're executable documentation of your business rules. When you say "we'll enforce that in the application layer", you're saying "we trust that no developer will ever make a mistake, no migration will ever skip a check, and no one will ever touch this data with raw SQL." That trust is misplaced.

3
Normalise First, Denormalise Later
Start strict. Loosen only with evidence.

Begin every design in at least 3NF. Only denormalise when you have a proven, measured performance problem that can't be solved with better queries or indexes. Premature denormalisation creates the same maintenance burden as premature optimisation in code. When you do denormalise, document why and which anomalies you're accepting.

4
Schema Is a Contract
Treat migrations like API versioning.

Your database schema is a public contract that multiple applications, services, and tools depend on. Changing it requires the same discipline as changing a public API: backward compatibility, migration plans, and communication. Use numbered migration scripts (Flyway, EF Migrations, Alembic) — never modify schemas by hand in production.

5
Design for Queries, Not for Objects
The database serves queries, not your class hierarchy.

Object-relational impedance mismatch is real. Don't blindly mirror your C# classes as database tables — class hierarchies, encapsulation, and polymorphism don't map cleanly to relational structures. Design your schema for the queries you'll run, then map to objects in application code. The ORM should adapt to the database, not the other way around.

6
Naming Is Design
Consistent, descriptive names prevent entire categories of bugs.

Pick a convention and enforce it ruthlessly. Singular or plural table names — pick one. Snake_case or PascalCase — pick one. Is it CustomerId or CustId or customer_id? When every developer has to guess the column name, errors multiply. Good naming makes the schema self-documenting.

7
Measure, Don't Guess
Use EXPLAIN ANALYZE, not intuition.

The database engine's query planner is smarter than your intuition. Before adding indexes, rewriting queries, or restructuring tables — profile. Look at actual execution plans, not estimated ones. The bottleneck is almost never where you think it is. Keep a performance baseline and track regressions.

8
Soft Delete with Caution
Deleted data is never really deleted — until it is.

Soft deletes (an IsDeleted flag) seem safe, but every query now needs WHERE IsDeleted = 0. Forget it once and your UI shows deleted data. Unique constraints break because the "deleted" row still occupies the unique slot. Consider alternatives: audit tables, event sourcing, or temporal tables (supported natively in SQL Server 2016+ and PostgreSQL).

9
The Log Is the Truth
Immutable event logs are more powerful than mutable state.

Kleppmann argues that an append-only log of events (every change that happened, in order) is a more fundamental data structure than the current state of a database. The current state is just a projection of the log. This philosophy — influenced by event sourcing and stream processing — means you can always rebuild state from the log, but you can never reconstruct the log from the state alone.

10
Understand Your Access Patterns
OLTP and OLAP are fundamentally different workloads.

Transactional systems (OLTP) optimise for many small reads and writes — a customer places an order, a user updates their profile. Analytical systems (OLAP) optimise for few large reads across millions of rows — "what was total revenue by region last quarter?" Trying to serve both from one schema without understanding this distinction is a recipe for neither working well. Ralph Kimball's dimensional modelling (star schemas, fact tables, dimension tables) exists specifically for this reason.

Further Study
Essential Reading

The books that shaped the principles on this page. Ordered roughly from most practical to most theoretical — start wherever matches your current need.

Designing Data-Intensive Applications
Martin Kleppmann · O'Reilly, 2017 (2nd ed. 2026)
The definitive guide to modern data systems. Covers replication, partitioning, transactions, consistency models, batch/stream processing. Teaches you to think in trade-offs rather than best practices. Widely considered the most important book for backend engineers.
MUST READ
SQL Antipatterns
Bill Karwin · Pragmatic Bookshelf, 2010 (Vol. 1 updated 2024)
A catalogue of the most common database design mistakes and how to fix them. Covers logical design (Jaywalking, EAV, Keyless Entry), physical design (Index Shotgun), query patterns (Spaghetti Query), and application integration. Extremely practical.
HIGHLY PRACTICAL
Database Design for Mere Mortals
Michael J. Hernandez · Addison-Wesley, 3rd ed.
The most accessible guide to relational database design. Walks through the full process: analysing requirements, defining tables, establishing relationships, enforcing business rules, and creating views. No prior database experience required.
BEGINNER FRIENDLY
An Introduction to Database Systems
C.J. Date · Addison-Wesley, 8th ed.
The academic standard — 900,000+ copies sold. Rigorous treatment of relational theory, normalisation, and the relational algebra that underpins SQL. Dense but authoritative. Date pioneered relational database technology alongside Codd at IBM.
FOUNDATIONAL THEORY
The Data Warehouse Toolkit
Ralph Kimball & Margy Ross · Wiley, 3rd ed.
The definitive guide to dimensional modelling — star schemas, fact tables, slowly changing dimensions. Essential if you work with reporting, business intelligence, or analytics. The OLTP vs OLAP distinction crystallised here.
ANALYTICS / BI
Database Internals
Alex Petrov · O'Reilly, 2019
Goes deep on how databases work under the hood — storage engines (B-Trees, LSM Trees), transaction processing, distributed system protocols (Raft, Paxos). Excellent companion to DDIA for understanding why databases behave the way they do.
