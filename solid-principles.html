// Object-Oriented Design

SOLID

Five principles for writing maintainable, flexible, and scalable object-oriented code — illustrated with real before/after examples.

S — Single Responsibility O — Open/Closed L — Liskov Substitution I — Interface Segregation D — Dependency Inversion
S
Single Responsibility Principle
One class, one reason to change.

A class should have only one job. When a class handles multiple concerns, a change in one area forces you to retest and redeploy everything — even unrelated functionality.

Before — Violation UserService.cs 
// ❌ This class does WAY too much.
// Changing email logic forces retesting
// user data logic, and vice versa.

public class UserService
{
    public void CreateUser(User user)
    {
        // Save to database
        _db.Insert(user);

        // Format and send welcome email
        var body = $"Welcome, {user.Name}!";
        var msg = new MailMessage(
            "noreply@app.com", user.Email,
            "Welcome!", body);
        new SmtpClient().Send(msg);

        // Generate and write audit log
        var log = $"[{DateTime.Now}] User created: {user.Id}";
        File.AppendAllText("audit.log", log);
    }
}
After — Fixed UserService.cs + others 
// ✅ Each class has one job.
// Swap email provider? Only EmailService changes.
// Change log format? Only AuditLogger changes.

public class UserService
{
    private readonly IEmailService _email;
    private readonly IAuditLogger _logger;

    public void CreateUser(User user)
    {
        _db.Insert(user);
        _email.SendWelcome(user);
        _logger.Log($"User created: {user.Id}");
    }
}

public class EmailService : IEmailService
{
    public void SendWelcome(User user) { /* ... */ }
}

public class AuditLogger : IAuditLogger
{
    public void Log(string msg) { /* ... */ }
}
⚠ The problem: A bug in the email SMTP config could break user creation entirely. You can't unit test user persistence without also setting up email and file I/O.
✓ The fix: Each class is independently testable and deployable. Mock IEmailService in tests and never touch real SMTP.
O
Open/Closed Principle
Open for extension. Closed for modification.

You should be able to add new behaviour without editing existing, tested code. Modifying working code risks introducing regressions; extending it via new classes is safe.

Before — Violation DiscountCalculator.cs 
// ❌ Every new discount type requires
// editing this method. Risk of breaking
// existing discount logic every time.

public class DiscountCalculator
{
    public decimal Calculate(
        Order order, string discountType)
    {
        if (discountType == "seasonal")
            return order.Total * 0.10m;

        else if (discountType == "loyalty")
            return order.Total * 0.15m;

        else if (discountType == "employee")
            return order.Total * 0.25m;

        // Adding "flash sale"? Edit this file again...
        return 0;
    }
}
After — Fixed Discounts/ 
// ✅ New discount = new class.
// DiscountCalculator never changes again.

public interface IDiscountStrategy
{
    decimal Calculate(Order order);
}

public class SeasonalDiscount : IDiscountStrategy
{
    public decimal Calculate(Order o) => o.Total * 0.10m;
}

public class FlashSaleDiscount : IDiscountStrategy
{
    public decimal Calculate(Order o) => o.Total * 0.40m;
}

public class DiscountCalculator
{
    private readonly IDiscountStrategy _strategy;

    public decimal Calculate(Order order)
        => _strategy.Calculate(order);
}
⚠ The problem: The if/else chain grows forever. Every new discount type touches the same battle-tested method, risking regression in unrelated branches.
✓ The fix: Strategy pattern. Add a "flash sale" discount by creating one new class — zero changes to anything that already works.
L
Liskov Substitution Principle
Subtypes must honour the base type's contract.

If S extends T, you should be able to use S anywhere T is expected without the program misbehaving. Subclasses that break or narrow inherited behaviour violate this principle.

Before — Violation Birds.cs 
// ❌ Penguin IS-A Bird, but it can't fly.
// Code that calls .Fly() on any Bird will
// crash or throw at runtime for Penguins.

public class Bird
{
    public virtual void Fly()
        => Console.WriteLine("Flap flap!");
}

public class Penguin : Bird
{
    public override void Fly()
        => throw new NotSupportedException(
            "Penguins can't fly!");
}

// Caller assumes all birds can fly:
void MakeAllBirdsFly(IEnumerable<Bird> birds)
{
    foreach (var b in birds) b.Fly(); // 💥 CRASH
}
After — Fixed Birds.cs 
// ✅ Separate the capability into interfaces.
// Only birds that CAN fly implement IFlyable.

public abstract class Bird
{
    public abstract void Move();
}

public interface IFlyable
{
    void Fly();
}

public class Eagle : Bird, IFlyable
{
    public override void Move() => Fly();
    public void Fly() => Console.WriteLine("Soar!");
}

public class Penguin : Bird
{
    public override void Move()
        => Console.WriteLine("Waddle waddle!");
}

void MakeFly(IEnumerable<IFlyable> flyers)
{
    foreach (var f in flyers) f.Fly(); // ✅ Safe
}
⚠ The problem: Penguin overrides Fly() to throw, silently breaking the contract every caller relies on. Polymorphism becomes a runtime minefield.
✓ The fix: Model capabilities as interfaces. IFlyable only applies to birds that actually fly. No surprises, no defensive try/catch around every Fly() call.
I
Interface Segregation Principle
Don't force clients to depend on methods they don't use.

A fat interface forces every implementor to stub out irrelevant methods. Prefer many small, focused interfaces over one large one — callers only depend on what they actually need.

Before — Violation IDevice.cs 
// ❌ A basic printer can't scan or fax.
// It's forced to implement methods
// that throw NotImplementedException.

public interface IDevice
{
    void Print(Document d);
    void Scan(Document d);
    void Fax(Document d);
}

public class BasicPrinter : IDevice
{
    public void Print(Document d) { /* real code */ }

    public void Scan(Document d)
        => throw new NotImplementedException();

    public void Fax(Document d)
        => throw new NotImplementedException();
}
After — Fixed IDevice.cs 
// ✅ Split into focused interfaces.
// Each class implements only what it can do.

public interface IPrinter  { void Print(Document d); }
public interface IScanner  { void Scan(Document d);  }
public interface IFax      { void Fax(Document d);   }

// Basic printer: just printing, no stubs needed
public class BasicPrinter : IPrinter
{
    public void Print(Document d) { /* real code */ }
}

// All-in-one: implements everything it supports
public class AllInOnePrinter : IPrinter, IScanner, IFax
{
    public void Print(Document d) { /* ... */ }
    public void Scan(Document d)  { /* ... */ }
    public void Fax(Document d)   { /* ... */ }
}
⚠ The problem: Any code that calls Scan() on a BasicPrinter explodes at runtime. The fat interface leaks implementation limitations into the type system.
✓ The fix: Small, role-based interfaces. A function that needs scanning depends on IScanner — it can't even receive a BasicPrinter by accident.
D
Dependency Inversion Principle
Depend on abstractions, not concretions.

High-level business logic should not be coupled to low-level infrastructure. Both should depend on a shared interface. This is the foundation of dependency injection and testability.

Before — Violation OrderService.cs 
// ❌ OrderService creates its own dependencies.
// Switching to Postgres? Edit business logic.
// Unit testing? Real SQL Server required.

public class OrderService
{
    private readonly SqlServerDb _db;
    private readonly SmtpEmailSender _email;

    public OrderService()
    {
        _db    = new SqlServerDb("Server=prod;...");
        _email = new SmtpEmailSender("mail.corp.com");
    }

    public void PlaceOrder(Order order)
    {
        _db.Save(order);
        _email.Send(order.CustomerEmail,
            "Order confirmed!");
    }
}
After — Fixed OrderService.cs 
// ✅ Depend on interfaces injected from outside.
// Swap SqlServer → Postgres = 0 changes here.
// Tests pass in fakes — no real DB needed.

public interface IOrderRepository { void Save(Order o); }
public interface IEmailSender     { void Send(string to, string msg); }

public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly IEmailSender     _email;

    // Dependencies injected — not newed up inside
    public OrderService(IOrderRepository repo,
                        IEmailSender email)
    {
        _repo  = repo;
        _email = email;
    }

    public void PlaceOrder(Order order)
    {
        _repo.Save(order);
        _email.Send(order.CustomerEmail,
            "Order confirmed!");
    }
}
⚠ The problem: The constructor hard-codes a SQL Server connection string and a specific SMTP host. Business logic is glued to infrastructure — impossible to test in isolation.
✓ The fix: Inject interfaces. Your DI container (e.g. Microsoft.Extensions.DependencyInjection) wires up the real implementations in production; tests use Mock<IOrderRepository>. No infrastructure required.
