Naming

Naming Conventions

Conventions for writing clear, consistent, and meaningful names — naming is hard, but it's worth getting right.

  • Consistency
  • Domains + Verbs
  • Clarity
  • Booleans
  • Abbreviations
Naming is the most underestimated form of abstraction. A well-named variable, function, or class encodes intent — reducing the need for comments, making refactoring safer, and making code review faster. The time spent choosing a good name is paid back every time it is read.
Consistency

Consistency Over Personal Style — Document and Follow Your Naming Conventions

1
Consistency — Rule
Don't mix naming conventions in the same codebase — pick one and enforce it

Mixing getUser, fetch_user, getUserData, and retrieveUser for the same concept is a naming debt. It signals four different decisions made by four different people (or one person on four different days). One consistent pattern is better than four individually better alternatives.

Inconsistent — Avoiduser-repo.js
# ❌ Four patterns for the same concept in one file
async function getUser(id) {}       // camelCase
async function fetch_user(id) {}     // snake_case
async function getUserData(id) {}   // camelCase + "Data" suffix
async function retrieveUser(id) {}   // different verb
-- Which one is the canonical method?
-- Code review debates about which pattern to use.
-- New developers don't know which to use — adds friction.
Consistent — Preferreduser-repo.ts
# ✓ One convention, applied consistently
async function getUser(id: string): Promise<User> {}
async function getUserByEmail(email: string): Promise<User | null> {}
async function createUser(data: CreateUserDto): Promise<User> {}
async function updateUser(id: string, data: UpdateUserDto): Promise<User> {}
async function deleteUser(id: string): Promise<void> {}
-- One verb (get), consistent parameter order, consistent return types.
-- A new developer reads one function and understands all of them.
-- A lint rule can enforce this automatically.
2
Consistency — Scope
Match the language's standard library conventions and the team's established patterns

JavaScript/TypeScript: camelCase for variables/functions, PascalCase for classes/types. Python: snake_case for functions/variables, PascalCase for classes. Go: PascalCase for exported names, snake_case for unexported. Follow the language idiom before imposing your own preferences.

Domains + Verbs

Name for the Domain — Not the Implementation

1
Domain — Rule
Name things after business concepts, not technical implementation

A variable called tempArray describes what it is (a temporary array). A variable called pendingOrders describes what it means in the domain. A function called processQueue describes what it does technically. A function called fulfilBackloggedOrders describes what it does for the business. Domain names are meaningful to everyone; technical names are meaningful only to developers.

Technical name — Avoidorders.ts
# ❌ Names describe implementation, not domain meaning
const tempArray = orders.filter(o => o.status === 'pending');
const data = await db.select('orders', { type: 'backlog' });
function processQueue(items: any[]) { ... }
-- tempArray: what makes it temporary? Will it be renamed later?
-- data: what kind of data? Orders? Users? Anything?
-- processQueue: what is being processed? What is the queue?
Domain name — Preferredorders.ts
# ✓ Names reflect business domain, not implementation
const pendingOrders = orders.filter(o => o.status === 'pending');
const backloggedOrders = await orderRepo.findBacklogged();
function fulfilBackloggedOrders(orders: Order[]): Promise<void> {
  for (const order of orders) {
    await order.fulfil();
  }
-- pendingOrders: clear business meaning to anyone reading this code.
-- fulfilBackloggedOrders: business operation, not a technical process.
-- Domain experts and developers share vocabulary.
2
Domain — Verbs
Use verbs for functions/methods, nouns for variables/classes

Functions are actions — they do something. validateEmail(), createOrder(), calculateDiscount(). Classes and variables are things — they represent something. Order, discountRate, emailValidator. Consistent verb/noun usage makes code read naturally.

Functions: validateEmail, createOrder, calculateDiscount, sendNotification Classes: Order, UserService, EmailValidator, PaymentGateway Variables: pendingOrders, currentUser, discountRate
Clarity

Clarity Is More Important Than Brevity

1
Clarity — Rule
Prefer clarity over brevity — long names that explain are better than short names that don't

Code is read more often than it is written, and almost never in the context in which it was written. A name that takes a moment to understand is a name that slows down every reader, every time. The cost of a slightly longer name is paid once at write time; the cost of an unclear name is paid by every reader, forever.

Too brief — Avoidbilling.ts
# ❌ Abbreviations that obscure meaning
const p = orders.filter(o => o.status === 'p');  // p for pending?
const r = await api.get('/usr/' + id);  // r for response? resource?
function calc(tx: Tx): number { ... }  // calc what? calc where from?
-- p: does this mean pending? paid? processing?
-- r: what is the response? An order? A user?
-- calc: this might be fine today, but what when you add a calc for tax?
Clear name — Preferredbilling.ts
# ✓ Names that carry their meaning with them
const pendingOrders = orders.filter(o => o.status === 'pending');
const user = await api.get('/users/' + id);
function calculateOrderTotal(order: Order): number { ... }
-- pendingOrders: immediately clear to any reader.
-- user: not ambiguous — it's the resource we fetched.
-- calculateOrderTotal: specific, no ambiguity about what or where.
2
Clarity — Units
Encode units in variable names when the unit is not obvious from the type

A variable called timeout with value 3000 is ambiguous — is it 3000ms? 3000 seconds? A variable called timeoutMs is unambiguous. If the type system encodes the unit (e.g., Duration.ofMillis(3000)), the name can be simpler.

No unit — Avoidconfig.ts
# ❌ Implicit units — requires reading the usage to understand
const TIMEOUT = 3000;      // ms? seconds?
const MAX_SIZE = 10;      // 10 bytes? 10MB? 10 requests?
const THROTTLE = 100;     // 100 what?
Units in name — Preferredconfig.ts
# ✓ Units explicit in the variable name
const TIMEOUT_MS = 3000;
const MAX_SIZE_BYTES = 10_485_760;  // 10MB
const THROTTLE_RPS = 100;  // requests per second
Booleans

Booleans Should Ask a Question

1
Booleans — Rule
Prefix booleans with is, has, can, should — never with a noun alone

A boolean called active requires a question: "is it active?" A boolean called isActive answers the question directly. admin is ambiguous — a boolean? A string? isAdmin is unambiguously a boolean that answers a question.

Noun boolean — Avoiduser.ts
# ❌ Boolean without a question prefix — ambiguous
const active = true;          // is active? was active? should be active?
const admin = true;           // is this an admin user?
const done = false;           // is done? was done? has done?
if (user.active) { ... }     // reads awkwardly
Question prefix — Preferreduser.ts
# ✓ Boolean names that ask a clear question
const isActive = true;      // is this user active?
const isAdmin = true;       // is this user an admin?
const isDone = false;       // is this task done?
const hasPermission = true; // does the user have permission?
const canEdit = true;       // can the user edit this resource?
if (user.isAdmin) { ... }   // reads naturally: "if user is admin"
Abbreviations

Only Abbreviate if the Abbreviation Is More Readable Than the Full Word

1
Abbreviations — Standard
Widely understood abbreviations (HTML, API, URL, ID, DB) are fine — all others must be defined

HTML, API, URL, ID, DB, HTTP, SQL — these are more readable than their expansions (HyperText Markup Language). But tx for "transaction" or svc for "service" are not universal. If your team has to look up or ask about an abbreviation, it is not helping.

HTML, API, URL, ID, DB, HTTP, SQL, JSON, XML, CLI tx, amt, qty, svc, proc, msg, dt, bgn — not universal
