GRASP

General Responsibility Assignment Software Patterns. Where SOLID tells you how to structure individual classes, GRASP tells you who should be responsible for what. These nine patterns are the vocabulary for reasoning about responsibility assignment across an object model. You've been applying most of them intuitively — this just names them.

IE
Information Expert
Assign responsibility to the class that has the information to fulfil it.
most fundamental GRASP pattern avoids feature envy

The class that knows the most about a piece of data should be the one doing the work with it. Putting logic in the wrong class leads to "feature envy" — a class constantly reaching into another to do its job.

Violation OrderController.cs 
// ❌ OrderController knows about Order internals
// to calculate the total. OrderController is NOT
// the information expert — Order is.

public class OrderController
{
    public decimal GetTotal(Order order)
    {
        decimal total = 0;
        foreach (var line in order.Lines)
            total += line.Qty * line.UnitPrice;
        return total;
    }
}
Fixed Order.cs 
// ✅ Order knows its own lines — it IS
// the information expert. Total calculation
// belongs right here.

public class Order
{
    public decimal Total =>
        Lines.Sum(l => l.Qty * l.UnitPrice);
}

public class OrderController
{
    public decimal GetTotal(Order order)
        => order.Total; // just ask the expert
}
⚠The problem: Controller reaches into Order's data to do Order's math. If line pricing logic changes, you hunt through controllers, services, and views to find duplicated calculations.
✓The fix: The entity that owns the data computes the result. Callers just ask. This is Information Expert — and it's why your ERP domain objects should calculate their own totals, not your service layer.
CR
Creator
Assign creation of an object to the class that contains or closely uses it.
factory pattern foundation reduces coupling

B should create A if B contains A, closely uses A, has the initialising data for A, or records A. This avoids scattered new calls across unrelated classes.

Violation OrderService.cs 
// ❌ OrderService creates OrderLine objects
// even though Order is the natural owner.
// If OrderLine's constructor changes, all
// service methods break.

public void AddItem(Order order,
    Product p, int qty)
{
    var line = new OrderLine(p.Id, p.Price, qty);
    order.Lines.Add(line);
}
Fixed Order.cs 
// ✅ Order contains OrderLines — it's the
// Creator. The service just calls AddItem
// and Order encapsulates the construction.

public class Order
{
    public void AddItem(Product p, int qty)
    {
        Lines.Add(new OrderLine(p.Id,
            p.Price, qty));
    }
}

public void AddItem(Order order,
    Product p, int qty)
{
    order.AddItem(p, qty); // clean
}
✓Why it matters: When OrderLine gains a new required field, you update Order.AddItem() in one place — not every service and controller that was newing up lines.
LC
Low Coupling & High Cohesion
Classes should know little about each other, and do one thing well.
the two core tensions in design measured by change impact

These two patterns are always evaluated together. Low Coupling means a change in class A doesn't ripple into class B. High Cohesion means a class's methods all work toward the same purpose — it doesn't stray into unrelated concerns.

High Coupling + Low Cohesion ReportService.cs 
// ❌ Tightly coupled to SqlServerDb (concrete).
// Low cohesion: this class formats reports AND
// sends emails AND writes to disk.

public class ReportService
{
    private readonly SqlServerDb _db;
    private readonly SmtpClient _smtp;

    public void Run(Report r)
    {
        _db.Save(r);           // persistence
        _smtp.Send(r.Email);   // comms
        File.Write(r.Path, r); // storage
    }
}
Low Coupling + High Cohesion ReportService.cs 
// ✅ Depends on abstractions (interfaces).
// One responsibility: orchestrate.
// Each collaborator has its own cohesive job.

public class ReportService
{
    private readonly IReportRepo   _repo;
    private readonly INotifier     _notify;
    private readonly IFileExporter _export;

    public void Run(Report r)
    {
        _repo.Save(r);
        _notify.Send(r);
        _export.Write(r);
    }
}
💡The practical test: If a change to your email provider forces edits in a reporting class, coupling is too high. If your "user service" also handles logging, PDF generation, and cache invalidation, cohesion is too low.
CO
Controller
A non-UI class should receive and coordinate system events.
MVC foundation thin controllers

A Controller receives input from the UI layer and delegates to the domain — it doesn't contain business logic itself. This is the "thin controller, fat model" principle. You know this pattern from MVC in your .NET and Laravel work.

Fat Controller (violation) OrdersController.cs 
// ❌ Business logic living in the controller.
// Untestable without HTTP context.
// Every endpoint re-implements domain rules.

[HttpPost]
public IActionResult Place(OrderDto dto)
{
    if (dto.Lines.Count == 0)
        return BadRequest("No items");

    var discount = dto.IsVip ? 0.15m : 0;
    var total = dto.Lines.Sum(l =>
        l.Qty * l.Price) * (1 - discount);

    _db.Orders.Add(new Order { Total = total });
    _db.SaveChanges();
    return Ok();
}
Thin Controller (fixed) OrdersController.cs 
// ✅ Controller receives input, validates
// the shape, delegates to a service.
// Business rules live in the domain.

[HttpPost]
public async Task<IActionResult> Place(
    OrderDto dto)
{
    if (!ModelState.IsValid)
        return BadRequest(ModelState);

    var result = await _orderService
        .PlaceAsync(dto);

    return result.IsSuccess
        ? Ok(result.Value)
        : BadRequest(result.Error);
}
✓The payoff: Your OrderService.PlaceAsync() is testable in isolation — no HTTP stack, no database. The controller is so thin there's almost nothing to test in it directly.

DRY · YAGNI · KISS

Three complementary mantras for fighting the most common forms of code bloat: duplication, speculative complexity, and unnecessary cleverness. Together they describe what "clean code" actually means in practice.

DRY
Don't Repeat Yourself
Every piece of knowledge should have one single authoritative representation.
Hunt & Thomas, The Pragmatic Programmer not just copy-paste

DRY is often misunderstood as "never copy code." It's broader: if the same decision (business rule, constant, formula) appears in multiple places, a change to it requires you to find and update every copy — and you will eventually miss one. The fix is a single authoritative source.

Violation — Logic Duplication Various.cs 
// ❌ The GST rate is hardcoded in 3 places.
// When it changes from 15% to 16%, you'll
// find 2 of them. Bugs guaranteed.

// In InvoiceService.cs:
var gst = subtotal * 0.15m;

// In QuoteService.cs:
total = lineTotal + (lineTotal * 0.15m);

// In ReceiptPrinter.cs:
gstAmount = amount / 1.15m * 0.15m;
Fixed — Single Source of Truth TaxConstants.cs 
// ✅ One place. One change when the rate
// changes. No hunt. No misses.

public static class Tax
{
    public const decimal GstRate = 0.15m;
    public static decimal Gst(decimal amount)
        => amount * GstRate;
    public static decimal ExclGst(decimal total)
        => total / (1 + GstRate);
}

// Everywhere else:
var gst = Tax.Gst(subtotal);
⚠Watch out for WET code: "Write Everything Twice" (or more). Magic numbers, duplicated validation rules, copy-pasted SQL fragments — all DRY violations. The fix isn't always extraction into a method; sometimes it's a constant, a config value, or a shared schema.
YN
You Ain't Gonna Need It
Don't build features until you actually need them.
Extreme Programming (XP) fights speculative generalisation

Speculative generalisation — building abstractions for hypothetical future requirements — creates complexity with no current payoff. The requirements you imagine rarely arrive in the form you imagined. Build what you need now; refactor when the real need appears.

Violation — Over-Engineered NotificationSystem.cs 
// ❌ "We might need SMS, push, Slack, webhooks
// later." So a plugin system, factory registry,
// config-driven pipeline... for sending one email.

public interface INotificationChannel { ... }
public class NotificationChannelFactory { ... }
public class NotificationPipelineBuilder { ... }
public class ChannelRegistry { ... }
public class NotificationRouter { ... }

// Actual current requirement: send a welcome email.
// None of this complexity is needed yet.
Fixed — Just What's Needed EmailNotifier.cs 
// ✅ Build exactly what the current story needs.
// When SMS is actually requested, extract the
// interface then. The YAGNI code is also
// cheaper to delete if requirements change.

public class EmailNotifier
{
    public async Task SendWelcome(User user)
    {
        await _smtp.SendAsync(
            user.Email,
            "Welcome!",
            $"Hi {user.Name}...");
    }
}
💡The tension with SOLID: OCP says "design for extension." YAGNI says "don't over-abstract." The reconciliation: apply OCP to the places you know will vary (from domain knowledge), not to everything that could vary.
KISS
Keep It Simple, Stupid
Prefer the simplest solution that works. Complexity is a liability.
Lockheed Skunk Works, 1960 Occam's razor for code

Complex solutions are harder to read, debug, and maintain — and they fail in harder-to-diagnose ways. Every clever abstraction, nested ternary, and macro-pattern is debt that future-you pays with interest. If a junior dev can't follow it, it's too complex.

Violation — Unnecessary Cleverness StatusHelper.cs 
// ❌ A single lookup table, generic type magic,
// and reflection — to return a display string
// for an enum. Impressive? Yes. Necessary? No.

public static string GetLabel<T>(T value)
    where T : Enum
{
    return typeof(T)
        .GetMember(value.ToString())[0]
        .GetCustomAttribute<DisplayAttribute>()
        ?.Name ?? value.ToString();
}

// Called exactly once, for OrderStatus.
Fixed — Obvious and Direct OrderStatus.cs 
// ✅ Readable in 5 seconds. Easy to extend.
// No reflection, no generics, no magic.
// If you need it for 10 enums later,
// extract it then.

public static string ToLabel(OrderStatus s)
    => s switch
    {
        OrderStatus.Pending   => "Pending",
        OrderStatus.Shipped   => "Shipped",
        OrderStatus.Delivered => "Delivered",
        _                     => s.ToString()
    };
✓The rule of thumb: The measure of good code is how long it takes a new team member to understand it, not how few lines it is. A clear 15-line method beats a clever 5-line one every time.

The Twelve-Factor App

A methodology for building modern, cloud-native SaaS applications — published by Heroku engineers and now the de-facto checklist for any containerised deployment. Directly applicable to your Docker + Ubuntu Server parish platform and any cloud work you're targeting in the Auckland job market.

① Codebase

One codebase tracked in version control, many deploys. Never share code between apps by copying files — use a package/library. One repo = one app.

② Dependencies

Explicitly declare and isolate all dependencies. A .NET app should declare everything in .csproj; never rely on system-level packages being present on the host.

③ Config

Store config in environment variables — never in code. Connection strings, API keys, feature flags: env vars, not appsettings.Production.json committed to git.

④ Backing Services

Treat databases, queues, and email providers as attached resources. A local Postgres and an RDS Postgres are interchangeable — only the connection string changes.

⑤ Build, Release, Run

Strictly separate build (compile), release (combine build + config), and run (execute) stages. A release is immutable — never patch running code.

⑥ Processes

Execute the app as one or more stateless processes. Don't store user sessions in memory or on local disk — use Redis or a database. Any instance can die and be replaced.

⑦ Port Binding

Export services via port binding. The app is self-contained and listens on a port — it doesn't rely on being injected into a runtime (e.g. IIS). Kestrel in .NET is the twelve-factor way.

⑧ Concurrency

Scale out via the process model. Add more containers/instances, not bigger servers. Stateless processes make this trivial — no coordination needed between instances.

⑨ Disposability

Fast startup, graceful shutdown. A container should be killable at any moment without data loss. Use database transactions and message queue acknowledgements to handle mid-flight work.

⑩ Dev/Prod Parity

Keep development, staging, and production as similar as possible. Docker solves most of this — the same image runs locally and in production. Eliminates "works on my machine."

⑪ Logs

Treat logs as event streams. Write to stdout/stderr; let the platform (Docker, cloud) aggregate them. Don't manage log files in the app — use structured logging like Serilog.

⑫ Admin Processes

Run admin and management tasks as one-off processes — migrations, seed scripts, data fixes. They should run in the same environment as the app, not as cron jobs on the host.

III
Deep Dive — Factor III: Config
The most commonly violated factor. Never commit secrets to source control.
critical for Docker deployments directly relevant to your parish platform
Violation appsettings.Production.json 
// ❌ Secrets in a file committed to git.
// Rotate a key? New commit. New deployment.
// Leaked to git history forever.

{
  "Database": {
    "ConnectionString": "Server=prod-db;
      User=sa;Password=Prod$ecret99!"
  },
  "Smtp": {
    "ApiKey": "SG.xxxxxxxxxxxxxxxxxxx"
  }
}
Fixed — Environment Variables docker-compose.yml + Program.cs 
// ✅ Config lives in environment, not code.
// docker-compose.yml (never committed):

environment:
  - DATABASE_URL=Server=prod-db;User=sa;...
  - SMTP_API_KEY=SG.xxx

// Program.cs reads from env:
builder.Configuration
    .AddEnvironmentVariables();

// Or use .env file (in .gitignore) locally,
// secrets manager (AWS/Azure) in production.
⚠Real-world consequence: Thousands of production databases are compromised every year because a developer committed a connection string. Git history is permanent — even if you delete the file, the secret remains in history.

FIRST Principles

Five properties that every good unit test should have. These aren't suggestions — tests that violate them erode confidence in your test suite and eventually get skipped or deleted. Pairs naturally with TDD and the Testing Pyramid.

F
Fast
Tests must run in milliseconds, not seconds.

Slow tests don't get run. If the test suite takes 5 minutes, developers stop running it locally and only find failures on CI — after the code is already pushed. Unit tests that hit real databases, HTTP endpoints, or disk are integration tests, not unit tests.

Slow — Hits Real DBOrderTests.cs
// ❌ Spins up a real SQL Server connection.
// ~800ms per test. 300 tests = 4 minutes.

[Fact]
public async Task PlaceOrder_SavesCorrectly()
{
    var db = new SqlServerDbContext(realConnStr);
    var svc = new OrderService(db);
    await svc.PlaceAsync(testOrder);
    var saved = await db.Orders.FindAsync(1);
    Assert.NotNull(saved);
}
Fast — Mocked DependencyOrderTests.cs
// ✅ Mocked IOrderRepository. ~2ms per test.
// No database. No network. Just logic.

[Fact]
public async Task PlaceOrder_CallsRepo()
{
    var repo = new Mock<IOrderRepository>();
    var svc  = new OrderService(repo.Object, ...);

    await svc.PlaceAsync(testOrder);

    repo.Verify(r => r.Save(
        It.IsAny<Order>()), Times.Once);
}
I
Isolated (Independent)
Tests must not depend on each other or on shared state.

A test that passes in isolation but fails when run after another test is a ticking time bomb. Shared static state, shared databases, or test ordering assumptions all cause this. Each test must set up and tear down its own world.

⚠Common culprit: A static counter or singleton that one test increments, causing the next test's assertion to fail. Use [SetUp]/[TearDown] or fresh instances per test.
R
Repeatable
A test must produce the same result every run, on any machine.

Flaky tests — ones that sometimes pass and sometimes fail without code changes — are worse than no tests. They erode trust in the suite. Common causes: DateTime.Now, random values, network calls, environment-specific paths.

Non-RepeatableExpiryTests.cs
// ❌ Test passes today, fails tomorrow.
// DateTime.Now makes the result time-dependent.

[Fact]
public void Token_IsExpired()
{
    var token = new Token(DateTime.Now.AddHours(-2));
    Assert.True(token.IsExpired());
    // Breaks if clock skew or timezone differs.
}
Repeatable — Injected ClockExpiryTests.cs
// ✅ Inject a deterministic IClock.
// The test controls time — always consistent.

[Fact]
public void Token_IsExpired()
{
    var clock = new FakeClock(
        new DateTime(2026, 1, 1, 12, 0, 0));
    var token = new Token(
        clock.Now.AddHours(-2), clock);
    Assert.True(token.IsExpired());
}
S
Self-Validating
Tests must produce a clear pass or fail — no manual inspection required.

A test that writes output to the console and requires a developer to read it isn't a test — it's a manual check wrapped in test syntax. Use assertions. The result should be unambiguous: green or red.

⚠Anti-pattern: Console.WriteLine(result) inside a test with no Assert call. The test always passes — even when the output is wrong. If you need to inspect output, you need an assertion.
T
Timely
Write tests at the right time — ideally before or alongside the code.

Tests written long after the code are hard to write because the code wasn't designed for testability. Tests written before (TDD) or alongside code force good design decisions — you notice coupling and missing abstractions immediately because the test tells you.

💡The Testing Pyramid: Many fast unit tests (FIRST principles apply here), fewer integration tests (real DB, real HTTP), minimal E2E tests (browser automation). The pyramid shape is about confidence-per-cost ratio — unit tests are cheapest and fastest.

CIA Triad & OWASP Top 10

Security isn't a feature you add at the end — it's a lens you apply throughout design and implementation. The CIA Triad is the foundational model for what security actually means. The OWASP Top 10 is the canonical list of vulnerabilities every developer must know to avoid them.

CIA
The CIA Triad
Confidentiality · Integrity · Availability
foundational security model applies to every system you build

Confidentiality

Data is only accessible to those authorised to see it. Threats: data breaches, credential leaks, exposed APIs. Controls: encryption at rest and in transit (TLS), access control lists, least-privilege principles.

Integrity

Data is accurate and unaltered except by authorised processes. Threats: SQL injection modifying records, man-in-the-middle attacks. Controls: parameterised queries, checksums, signed tokens (JWT), audit logs.

Availability

Systems are accessible when needed by authorised users. Threats: DDoS, unhandled exceptions crashing services, misconfigured firewalls. Controls: rate limiting, health checks, redundancy, graceful error handling.

Applying the Triad

Ask of every feature: could this leak data (C)? Could this let data be modified unauthorised (I)? Could this cause downtime (A)? Any "yes" is a security requirement, not just a bug.

OW
OWASP Top 10
The ten most critical web application security risks — and how to prevent them.
OWASP 2021 edition required knowledge for any dev role

The Open Worldwide Application Security Project publishes this list to focus developers on the vulnerabilities that cause the most real-world breaches. Know these — you will be asked about them in senior dev interviews.

The 10 Critical Risks + Mitigations
A01 — Broken Access Control
     Users acting outside intended permissions.
     Fix: deny by default; check authorisation server-side every request.

A02 — Cryptographic Failures
     Sensitive data exposed due to weak/missing encryption.
     Fix: TLS everywhere, bcrypt for passwords, never roll your own crypto.

A03 — Injection (SQL, LDAP, OS command)
     Untrusted data sent to an interpreter as a command.
     Fix: parameterised queries, ORM usage, never string-concat SQL.

A04 — Insecure Design
     Missing threat modelling and secure design patterns.
     Fix: threat model early; apply defence in depth.

A05 — Security Misconfiguration
     Default credentials, verbose error messages, open cloud storage.
     Fix: security hardening checklists, remove defaults, suppress stack traces in prod.

A06 — Vulnerable & Outdated Components
     Libraries with known CVEs still running in production.
     Fix: Dependabot / NuGet audit; patch regularly.

A07 — Identification & Authentication Failures
     Weak passwords, missing MFA, broken session management.
     Fix: use a proven identity library (ASP.NET Identity, Auth0); enforce MFA.

A08 — Software & Data Integrity Failures
     Unsigned updates, deserialisation of untrusted data.
     Fix: verify signatures; use safe deserialisation.

A09 — Security Logging & Monitoring Failures
     Breaches go undetected for months due to no alerting.
     Fix: log auth events, failed access attempts; alert on anomalies.

A10 — Server-Side Request Forgery (SSRF)
     App fetches a remote resource from attacker-controlled URL.
     Fix: allowlist outbound URLs; validate & sanitise all user-supplied URLs.
A03
Deep Dive — A03: SQL Injection
The oldest, most famous, still happening vulnerability.

SQL injection is trivially preventable — yet it still appears in production codebases. It costs nothing to fix and everything when exploited. If you have any string-concatenated SQL anywhere in your ERP codebase, this is the one to audit first.

Vulnerable — String ConcatUserRepo.cs
// ❌ Input: username = "' OR '1'='1"
// Resulting query:
// SELECT * FROM Users WHERE Name='' OR '1'='1'
// Returns every user in the table.

public User Find(string username)
{
    var sql = "SELECT * FROM Users " +
              "WHERE Name='" + username + "'";
    return _db.ExecuteQuery(sql).FirstOrDefault();
}
Safe — ParameterisedUserRepo.cs
// ✅ Parameter is treated as data, never as SQL.
// Injected SQL is just a string — harmless.

public User Find(string username)
{
    // Dapper:
    return _conn.QueryFirstOrDefault<User>(
        "SELECT * FROM Users WHERE Name = @Name",
        new { Name = username });

    // Or EF Core (always parameterised):
    return _db.Users
        .FirstOrDefault(u => u.Name == username);
}
⚠Classic attack: ' OR '1'='1 bypasses login. '; DROP TABLE Users; -- deletes your data. Parameterised queries make these impossible — the database treats input as literal string values, never as executable SQL.
