Code Review

Code Review Principles

Conventions for what to look for, how to give feedback, and what authors should do before requesting review.

  • What to Review
  • Giving Feedback
  • Author Responsibilities
  • Tone and Respect
Code review is a collaboration, not a gatekeeping exercise. A good review improves the code, teaches both parties something, and strengthens the team's shared understanding. A bad review creates resentment, slows the team down, and doesn't catch the bugs that matter.
What to Review

Review the Intent, Not Just the Implementation

1
Review — Focus
The primary job of a reviewer is to catch bugs — not to enforce style preferences

If the CI pipeline passes and there are no linting errors, style is not a reviewer's job. Review for correctness: does this code do what the PR description says it does? Are edge cases handled? Could this break in production? Is the error handling right? Style is automated — correctness is not.

Correctness: logic, edge cases, error handling, security Design: does this fit the architecture? Is it the right abstraction? Readability: can future maintainers understand this? Style (already linted): let the CI handle it
2
Review — Discipline
Read every changed line — don't skim, don't trust the diff summary

Skimming a PR diff is not reviewing code. The diff summary hides context. The real bugs are often in the small, "obvious" changes that don't seem worth looking at twice. Read every line of every file changed. If you don't have time to read it properly, don't review it — defer to someone who does.

3
Review — Perspective
Review from the caller's perspective — not the author's

The author knows what the code is trying to do. The reviewer doesn't — they have to infer it from the code. If the code requires the reviewer to understand the author's mental model to follow it, the code is not clear enough. A good reviewer asks: "would a new team member understand this in six months?"

Giving Feedback

Feedback Is a Gift — Give It That Way

1
Feedback — Specificity
Be specific — "this is wrong" is not feedback, "this returns 404 when the user doesn't exist but should return 401 when the token is invalid" is feedback

General feedback forces the author to reverse-engineer your thinking. Specific feedback shows your reasoning and gives the author something concrete to act on. It also forces you to be precise — vague feedback often means you haven't fully understood the problem yourself.

Vague feedback — Avoidgithub.com
# ❌ Vague comment — forces author to guess the reasoning
"This doesn't look right."
"Why is this here?"
"This could be simplified."
-- "Doesn't look right" doesn't explain WHAT is wrong or WHY.
-- Author must spend time interpreting vague feedback.
-- No guidance on how to fix it.
Specific feedback — Preferredgithub.com
# ✓ Specific: describes what, why, and suggests a path forward
"This returns 404 when the user doesn't exist, but per the API
contract (see issue #42), a missing user should return 404, while
an invalid auth token should return 401. Currently, both return 404.
The fix would be to check token validity before querying the user."
-- Clear WHAT is wrong: 404 vs 401 semantics confused.
-- Clear WHY it's wrong: API contract in issue #42.
-- Clear HOW to fix: check token validity first.
2
Feedback — Priority
Distinguish between blocking issues, suggestions, and nitpicks — label them

Not all feedback is equal. A blocking issue (must fix before merge) is different from a suggestion (author's call) which is different from a nitpick (optional polish). Label each comment clearly so the author knows what must happen vs what is optional. If everything is "blocking", nothing is.

[blocking] — must fix before merge [suggestion] — author's decision, explain your reasoning [nit] — optional polish, tiny improvement
3
Feedback — Author
Respond to every review comment — even if just to acknowledge it

Every open review thread represents an unresolved question. Resolve every thread: either fix the issue, explain why you disagree (respectfully and with reasoning), or mark it as acknowledged. Don't leave threads open silently. If you disagree with feedback, say so — with reasoning, not with silence or a passive "I disagree".

Author Responsibilities

Authors Set Reviewers Up for Success

1
Author — Responsibility
Keep PRs small — a PR that needs a 2-hour review will be reviewed poorly or not at all

Review quality degrades as PR size increases. A 2,000-line PR reviewed in a hurry catches fewer bugs than a 150-line PR reviewed carefully. If your PR is large, the reviewer will miss something. Break it into logical pieces, merged incrementally — each piece independently reviewable.

2
Author — Testing
Write the tests before requesting review — and demonstrate they pass

A PR without tests is a PR that hasn't demonstrated its correctness. Write the tests that show the code works, then request review. If the CI is red when you request review, you are asking the reviewer to debug your CI — which is not their job. Green CI is a precondition for review, not a courtesy.

Requesting review with CI red: reviewer will ask you to fix CI first Green CI + tests demonstrating the fix: ready for substantive review
3
Author — Context
Self-review before requesting review — read your own diff like a reviewer would

Before requesting review, read your own diff. Read it as if you've never seen it before. Does it make sense? Are there debugging artifacts (console.log, commented-out code, TODO comments left in)? Are the variable names clear? This catches 80% of the issues a reviewer would find — and the remaining 20% are the interesting ones that actually benefit from a second pair of eyes.

Tone and Respect

Review the Code, Not the Coder

1
Tone — Rule
Critique the code, not the author — "this is wrong" vs "you are wrong"

"This is wrong" is a statement about the code. "You are wrong" is a statement about the person. The first can be fixed with a code change. The second makes the author defensive. Reviewers: assume positive intent. Authors: assume the reviewer is trying to help, not to criticise.

Person-focused — Avoidgithub.com
# ❌ Feedback that attacks the person, not the code
"Why did you even do it this way? This is obviously wrong."
"You forgot to handle the null case again."
"This is a naive implementation."
-- Triggers defensiveness. Author focuses on defending themselves.
-- Doesn't help the author understand the actual issue.
-- Creates negative team dynamics.
Code-focused — Preferredgithub.com
# ✓ Feedback focused on the code, not the person
"This will throw if the user is null — we should handle that case.
Consider: if (!user) return early with a 401."
"This works, but a more concise alternative might be...
[suggestion] — no need to change if you prefer the current approach."
-- Describes the code issue, not the author's decision.
-- Offers a concrete suggestion without demanding it.
-- Explicitly notes when something is optional — reduces friction.
2
Tone — Balance
Acknowledge what's good — reviews that only flag problems breed resentment

A review that only says "fix this" and "fix that" is demoralising, even when all the comments are technically correct. Point out what's good: "this is a clean solution", "I like how you handled the edge case here", "this test coverage is thorough". Positive acknowledgment costs nothing and makes the constructive feedback land better.
