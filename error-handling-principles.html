Error Handling

Error Handling Principles

Conventions for failing fast, propagating errors, custom error types, and resilience patterns.

  • Fail Fast
  • Propagation
  • Custom Types
  • Resilience
Errors are not exceptional — they are expected. A robust system handles them gracefully at every layer. The question is not whether errors will occur, but whether your code is designed to handle them in a way that is debuggable, recoverable, and informative to the caller.
Fail Fast

Detect Errors at the Boundary — Not Deep in the Logic

1
Fail Fast — Rule
Validate inputs at the public interface — fail immediately with a clear message

A function that accepts invalid input and fails silently three call stacks deep is a debugging nightmare. Validate at the entry point of every public function. If the input is invalid, fail immediately, explicitly, and with enough context to understand what went wrong.

Deferred validation — Avoidorder-service.js
# ❌ Validation deferred to deep inside the call stack
async function placeOrder(itemId: number, userId: number) {
  // No validation here — passes straight through
  return this.orderRepo.create({ itemId, userId });
  // Validation happens inside the repo, on the database constraint
  // Error surfaces as: "PostgreSQL error: null value in column..."
}
-- Error surfaces as a raw database constraint violation.
-- No context about which parameter was invalid.
-- Requires database log investigation to debug.
Fail fast — Preferredorder-service.ts
# ✓ Validate at the entry point — fail fast with clear error
async function placeOrder(itemId: number, userId: number): Promise<Order> {
  if (!Number.isInteger(itemId) || itemId <= 0) {
    throw new ValidationError(`itemId must be a positive integer, got: ${itemId}`);
  }
  if (!Number.isInteger(userId) || userId <= 0) {
    throw new ValidationError(`userId must be a positive integer, got: ${userId}`);
  }
  return this.orderRepo.create({ itemId, userId });
-- Error is caught at the boundary, not three layers deep.
-- Message clearly identifies which parameter failed and why.
-- Stack trace points directly at the calling code.
2
Fail Fast — Invariant
Assert invariants that should never be violated — don't check things that can't be false

Use assertions for conditions that should be true if your code is correct — internal state that should never be reached in an invalid way. Don't use assertions for input validation (that's fail fast for external input). Assertions are for catching programming errors in development, not for handling runtime failures.

Error Propagation

Errors Should Gain Context as They Bubble Up

1
Propagation — Rule
Never swallow errors — add context when re-throwing

Catching an error and re-throwing with no information destroys the stack trace. Catching and adding context before re-throwing preserves the chain while giving future debuggers the context they need to understand the error's journey through your system.

Swallowed error — Avoidorder-service.js
# ❌ Error context destroyed — debugging nightmare
async function placeOrder(itemId: number) {
  try {
    const item = await this.itemService.get(itemId);
    return item.price;
  } catch (err) {
    throw new Error('Order failed');  ← original error destroyed
  }
}
-- Original error (item not found? network timeout? auth failure?)
-- is completely lost. The caller sees only "Order failed".
-- Stack trace no longer points to the real source of the problem.
Chained error — Preferredorder-service.ts
# ✓ Error carries its full history through the call stack
async function placeOrder(itemId: number): Promise<Order> {
  try {
    const item = await this.itemService.get(itemId);
    return item.price;
  } catch (err) {
    throw new OrderError(
      `Failed to place order for item ${itemId}`
      { cause: err }  ← chain preserved
    );
  }
-- Original error is chained via the `cause` property.
-- Full stack trace preserved.
-- Message tells you the context in addition to the root cause.
2
Propagation — Pattern
Use Result types (or discriminated unions) instead of throwing for expected failures

Not all errors are exceptional. A user not found, a resource not authorized, a validation failure — these are expected outcomes, not exceptions. Returning a Result<T, E> type (Rust-style: { ok: true, value: T } | { ok: false, error: E }) makes expected failures explicit in the type signature, forcing callers to handle them.

Result<T,E>: expected failures — not found, not authorized, validation throw: truly exceptional — invariant violated, bug, system failure
Custom Error Types

Errors Are Types — Give Them Structure

1
Custom Types — Rule
Don't throw generic Error objects — use typed errors with structured data

A string error message is not an error type. A structured error with a code, a message, a HTTP status mapping, and structured metadata is an error type. Callers can match on error type to take different recovery actions — something that is impossible with a raw string message.

Generic Error — Avoiderrors.js
# ❌ String-based error discrimination — fragile, untyped
if (!user) throw new Error('User not found');
if (!auth) throw new Error('Unauthorized');
if (!item) throw new Error('Item not found');
-- Caller: try { ... } catch (e) { if (e.message === 'User not found') ... }
-- String comparison is brittle: 'user not found', 'User not found' — which one?
-- No structured data: what was the userId that wasn't found?
-- No HTTP status mapping: API layer must guess which status to return.
Typed errors — Preferrederrors.ts
# ✓ Typed errors with structured data and HTTP mapping
class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly httpStatus: number,
    public readonly details?: Record<string, unknown>
  ) { super(message); this.name = 'AppError'; }
}
class NotFoundError extends AppError {
  constructor(entity: string, id: string) {
    super(`${entity} ${id} not found`, 'NOT_FOUND', 404, { entity, id });
  }
class UnauthorizedError extends AppError {
  constructor() { super('Unauthorized', 'UNAUTHORIZED', 401); }
-- Caller: catch (e) { if (e instanceof NotFoundError) { res.status(404)... } }
-- Type-safe discrimination. IDE autocomplete. Compiler catches missing cases.
-- Structured details: { entity: 'user', id: '42' } for logging.
Resilience

Degrade Gracefully — Don't Let One Failure Cascade

1
Resilience — Pattern
Use circuit breakers to prevent cascading failures

When a downstream service is failing, repeatedly calling it wastes resources and can cause your service to fail too. A circuit breaker tracks failure rates and, after a threshold is reached, "opens" — failing fast without making network calls. This gives the downstream service time to recover while your service continues to handle other requests.

Unbounded retries — Avoidpayment-client.js
# ❌ Retrying a failing service — resources wasted, cascading failure
async function charge(amount: number) {
  while (true) {  ← unbounded retry!
    try {
      return await paymentProvider.charge(amount);
    } catch (err) {
      await sleep(1000);  ← retry every second forever
    }
  }
-- Payment provider is down? This ties up a thread forever.
-- Each retry adds load to the failing service.
-- Users see hanging requests, not clear errors.
Circuit breaker — Preferredpayment-client.ts
# ✓ Circuit breaker: fail fast, recover gracefully
const circuit = new CircuitBreaker({
  failureThreshold: 5,   // open after 5 consecutive failures
  resetTimeout: 30_000, // try again after 30 seconds
});
async function charge(amount: number) {
  return circuit.execute(() => paymentProvider.charge(amount));
-- After 5 failures: opens circuit, fails immediately for 30s.
-- Downstream service gets breathing room to recover.
-- Your service degrades gracefully instead of hanging.
2
Resilience — Rule
Every network call must have a timeout — no infinite waits

A downstream service that never responds is indistinguishable from a network partition. Without a timeout, your service waits indefinitely, accumulating goroutines/threads until it runs out of resources. Every network call — HTTP, database, cache, external API — must have an explicit timeout.

3
Resilience — Pattern
Use bulkheads to isolate failures — don't let one subsystem take down all others

A bulkhead (named after watertight compartments in a ship) isolates failures so that one subsystem failing doesn't drain resources from others. For example, a separate thread pool for the payment service vs the notification service — if payments exhaust their pool, notifications continue to work.
