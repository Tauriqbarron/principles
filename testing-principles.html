Testing

Testing Principles

Conventions for writing tests that give you confidence to ship — test pyramid, unit, integration, E2E, mocking, and coverage philosophy.

  • Pyramid
  • Unit
  • Integration
  • E2E
  • Mocking

Tests are a communication contract with your future self. Write tests that are fast, deterministic, and reveal intent — tests that make refactoring safe rather than tests that just assert current implementation.
Test Pyramid

The Foundation of a Healthy Test Strategy

1
Pyramid — Shape
More unit tests than integration tests than E2E tests

The test pyramid isn't just a diagram — it's an economic constraint. Unit tests are fast and cheap to write and maintain. E2E tests are slow, brittle, and expensive. If you invert the pyramid, your test suite will slow you down, not speed you up.

Ice-cream cone — Avoid test-count.txt 
# ❌ Inverted pyramid — slow, expensive to run
E2E tests:       150  (slow, 5-30 min each)
Integration:     80   (medium, 500ms-5s each)
Unit tests:      40   (fast, <10ms each)
-- CI takes 45 minutes.
-- Flaky E2E tests block deployments.
-- Developers stop running tests locally.
Healthy pyramid — Preferred test-count.txt 
# ✓ Pyramid: fast feedback, expensive tests at the top
Unit tests:      400  (fast, <10ms each)    ~70%
Integration:     120  (medium, 100ms-1s)  ~20%
E2E tests:       30   (slow, 30s-5m each)  ~10%
-- Full suite runs in under 5 minutes.
-- E2E tests cover only critical user journeys.
-- Fast feedback loop keeps developers in flow.
2
Pyramid — Purpose
Each layer tests a different concern, not the same thing in different places

If your unit tests and E2E tests assert the same things, you have redundancy, not coverage. Each layer should test what the other layers cannot test — unit tests for logic, integration for data flow, E2E for critical user journeys.

Unit: logic & edge cases Integration: data flow & I/O E2E: critical user journeys
Unit Tests

Fast, Isolated, Meaningful

1
Unit — Scope
Test one concept per test function

A test that checks 10 things at once is a test that hides 9 potential failures. Each test should have a single, clear reason to fail. If you can't name your test after the behaviour it verifies, the test is doing too much.

Kitchen-sink test — Avoid order.test.js 
# ❌ One test checks everything
test('order workflow', () => {
  const order = createOrder();
  order.addItem(item);
  expect(order.items.length).toBe(1);
  order.applyDiscount('SAVE10');
  expect(order.total).toBe(90);
  order.status = 'shipped';
  expect(order.status).toBe('shipped');
  order.cancel();
  expect(order.status).toBe('cancelled');
  expect(order.refund).toBe(90);
})
-- If the discount fails, the rest never runs.
-- Failure message: "order workflow" — which part?
One concept per test — Preferred order.test.js 
# ✓ Each test is a single, named behaviour
test('addItem increases item count by one', () => {
  const order = createOrder();
  order.addItem(item);
  expect(order.items).toHaveLength(1);
})
test('SAVE10 reduces total by 10%', () => {
  const order = createOrder({ total: 100 });
  order.applyDiscount('SAVE10');
  expect(order.total).toBe(90);
})
test('cancel sets status to cancelled', () => {
  const order = createOrder();
  order.cancel();
  expect(order.status).toBe('cancelled');
})
2
Unit — Reliability
Tests must be deterministic — no randomness, no time dependencies

A test that sometimes passes and sometimes fails is worse than no test — it erodes trust in the entire suite. Mock the clock, freeze time, seed randomness. A flaky test should be treated as a broken test.

Non-deterministic — Avoid token.test.js 
# ❌ Random expiry — test sometimes fails
test('token is valid for 24 hours', () => {
  const token = generateToken({ ttl: 24 * 60 * 60 });
  const now = Date.now();
  const in25hrs = now + 25 * 60 * 60 * 1000;
  // ❌ Uses real clock — flakiness depends on when this runs
  expect(isTokenValid(token, { at: in25hrs })).toBe(false);
})
-- Passes on fast machines, fails on slow ones.
-- Fails when system clock is adjusted.
Frozen time — Preferred token.test.js 
# ✓ Deterministic — time is controlled and explicit
test('token is invalid after TTL expires', () => {
  const fixedNow = new Date('2025-01-01T12:00:00Z');
  const token = generateToken({
    ttl: 24 * 60 * 60,
    issuedAt: fixedNow,
  });
  const expiredTime = new Date('2025-01-02T12:00:01Z');
  expect(isTokenValid(token, { at: expiredTime })).toBe(false);
})
3
Unit — Readability
Test intent, not implementation

Tests that assert implementation details break on every refactor, even when behaviour is preserved. Tests should describe what the code does, not how it does it. When refactoring changes the internals without changing behaviour, tests should not need to change.

Implementation detail — Avoid user.test.js 
# ❌ Tests how, not what — breaks on refactor
test('user is saved to cache on login', async () => {
  const user = { id: 1, name: 'Alice' };
  await login(user);
  // ❌ Hardcoded cache key format — any refactor of the
  // cache key strategy breaks this test unnecessarily
  expect(cache.set).toHaveBeenCalledWith(
    'user:1',
    expect.anything()
  );
})
Behaviour-based — Preferred user.test.js 
# ✓ Tests what — survives refactor of internals
test('authenticated user is retrieved from cache on subsequent requests', async () => {
  const user = { id: 1, name: 'Alice' };
  await login(user);
  // ✓ Reads as documentation: user data is cached after login
  const cached = await getUser(1);
  expect(cached.name).toBe('Alice');
  // No cache.set call asserted — implementation detail
  // Changing cache key format won't break this test.
}
Integration

Test the Assembly, Not the Parts

1
Integration — Fidelity
Use real databases, real queues — not mocks

The whole point of an integration test is to verify that the interfaces between components work correctly. Mocking the database defeats the purpose. Use testcontainers, in-memory databases, or a dedicated test database instance.

Mocked DB — Avoid order-repo.test.js 
# ❌ Mocks hide real DB interface problems
jest.mock('../db');
test('order is saved', async () => {
  db.query.mockResolvedValue([{ id: 1 }]);
  // ✅ Test passes — but did the SQL actually work?
  // Does the column name match? Does the type coercion work?
  // Is the transaction isolation level correct?
  const result = await saveOrder({ name: 'Order 1' });
  expect(result.id).toBe(1);
})
Real DB — Preferred order-repo.test.js 
# ✓ Testcontainers — real PostgreSQL, real queries
test('order is saved and retrieved correctly', async () => {
  const container = await new PostgreSqlContainer().start();
  const repo = new OrderRepository(container.getConnection());
  // ✅ Column names, types, constraints — all verified against real DB
  const saved = await repo.save({ name: 'Order 1', total: 99.99 });
  expect(saved.id).toBeDefined();
  const retrieved = await repo.findById(saved.id);
  expect(retrieved.total).toBe(99.99);
  await container.stop();
})
2
Integration — Scope
Integration tests cover a service boundary end-to-end

An integration test should exercise the entire stack of a service — from the HTTP handler to the database — without mocking any layer. If you mock something inside the service boundary, you don't have an integration test, you have a unit test with extra steps.

E2E

Critical Paths Only

1
E2E — Scope
Only test critical user journeys as E2E tests

E2E tests are expensive to write, slow to run, and fragile. You cannot afford to have 200 of them. Choose 20–30 flows that represent the most important things your users do — sign-up, login, checkout, invite a friend. Everything else is covered by lower layers.

Sign-up and email verification Login and logout Core transaction flows
2
E2E — Selectors
Use test-specific data attributes, not CSS selectors

E2E tests that use CSS selectors or XPath break on every design change — even when the behaviour is correct. Use dedicated data-testid attributes or semantic HTML roles. The design team can refactor freely without breaking your tests.

CSS selector — Avoid login.spec.js 
# ❌ CSS selectors break on design changes
test('login button is clickable', async () => {
  await page.click('.login-form > div:nth-child(4) > button');
  // ❌ Any CSS refactor breaks this test.
  await expect(page.locator('.login-form')).toBeVisible();
})
data-testid — Preferred login.spec.js 
# ✓ data-testid — stable across design refactors
<button data-testid="login-submit" type="submit">Sign In</button>

test('login button is clickable', async () => {
  await page.click('[data-testid="login-submit"]');
  await expect(page.locator('[data-testid="login-submit"]')).toBeEnabled();
})
-- Design refactor: move button anywhere in DOM — test still passes.
Mocking

Control What You Own, Trust What You Don't

1
Mocking — Rule
Mock external dependencies — not your own modules

If you mock your own internal modules, you're not testing your code — you're testing your mocks. Mock the database client, the HTTP client, the cache client. But the classes and functions within your own codebase should be tested for real.

Mock own service — Avoid order-service.test.js 
# ❌ Mocking internal modules — what's actually being tested?
jest.mock('../order-repository');
jest.mock('../email-service');
test('order is placed', async () => {
  orderRepository.save.mockResolvedValue({ id: 1 });
  emailService.send.mockResolvedValue();
  // ❌ This is testing nothing — all real logic is mocked away.
  await orderService.placeOrder({ itemId: 1 });
  expect(orderRepository.save).toHaveBeenCalled();
})
Mock external — Preferred order-service.test.js 
# ✓ Only external I/O is mocked — real logic is exercised
jest.mock('../email-service');  // external: ✅ mock
// order-repository: real — ✅ integration test
test('placeOrder saves order and sends confirmation email', async () => {
  emailService.send.mockResolvedValue();
  // ✅ Real repository: SQL queries, constraints, transactions all exercised
  const order = await orderService.placeOrder({ itemId: 1, userId: 42 });
  expect(order.id).toBeDefined();
  expect(emailService.send).toHaveBeenCalledWith(
    expect.objectContaining({ to: expect.any(String), template: 'order-confirmed' })
  );
})
2
Mocking — Anti-pattern
Don't verify implementation details of mocked interactions

Verifying that a mock was called with specific arguments is a form of testing implementation. If you refactor the internal call sequence — even without changing behaviour — the test breaks. Verify outcomes, not interactions.

Interaction test — Avoid payment.test.js 
# ❌ Tests call order, not outcome
test('payment flow calls services in correct order', async () => {
  await paymentService.process(card);
  // ❌ This breaks if you add logging between two calls
  // even though the final outcome is identical
  expect(validateCard).toHaveBeenCalledBefore(chargeCard);
  expect(chargeCard).toHaveBeenCalledBefore(sendReceipt);
})
Outcome test — Preferred payment.test.js 
# ✓ Tests outcome, not call order
test('processPayment charges card and sends receipt', async () => {
  const result = await paymentService.process({
    card, amount: 99.99, customerId: 'cust_123'
  });
  // ✅ Verifies the final outcome — doesn't care about call order
  expect(result.status).toBe('charged');
  expect(result.receiptEmail).toBe('alice@example.com');
})
Coverage

Meaningful Coverage, Not Vanity Metrics

1
Coverage — Philosophy
High coverage does not mean well-tested code

You can have 100% line coverage with tests that assert nothing meaningful. A single sprawling test that calls every line once satisfies the metric but provides zero confidence. Coverage is a lower bound indicator, not a quality signal.

Vanity coverage — Avoid order.test.js 
# ❌ 100% line coverage — but what does it test?
test('order service', () => {
  const r = orderService;
  expect(r).toBeDefined();
  // ✅ 100% line coverage of order.js
  // ❌ Zero edge cases tested
  // ❌ Zero error paths tested
  // ❌ Zero boundary conditions tested
})
Meaningful tests — Preferred order.test.js 
# ✓ Fewer lines covered — but every edge case is tested
test('zero-quantity order throws InvalidQuantityError', () => {
  expect(() => createOrder({ quantity: 0 })).toThrow(InvalidQuantityError);
})
test('negative price order throws InvalidPriceError', () => {
  expect(() => createOrder({ price: -1 })).toThrow(InvalidPriceError);
})
test('order with maximum quantity is accepted', () => {
  const order = createOrder({ quantity: 10000 });
  expect(order.quantity).toBe(10000);
})
-- Lower line coverage than the vanity test.
-- Higher confidence in correctness.
2
Coverage — Metric
Use branch coverage, not just line coverage

Line coverage measures whether a line ran. Branch coverage measures whether every branch in a conditional was exercised — both the if and the else. A test suite with 100% branch coverage is meaningfully more trustworthy than one with 100% line coverage.

Line coverage: did this line run? Branch coverage: did both paths of every if/else run?
