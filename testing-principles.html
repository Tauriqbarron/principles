Testing Principles

Tests are a communication medium. A good test documents what the code does, what edge cases are handled, and what the intended behaviour is. Tests that don't communicate clearly are liabilities — they break for the wrong reasons and hide real bugs.
Test Pyramid

The Foundation: Fast, Focused, Many

✓

Write tests in this order: unit → integration → e2e

Unit tests are fast, cheap, and precise. Write the most of those. Integration tests verify that parts work together. E2E tests verify critical user journeys — sparingly.

✗

Don't build an ice-cream cone or hourglass

Too many E2E tests: slow, brittle, expensive to maintain. Too many integration tests: medium cost, medium brittleness. The pyramid shape exists for a reason — it reflects cost and feedback speed.

✓

Tests should run in isolation

No test should depend on another test running before it. Randomise test order. Parallelise where possible. A test that fails only when run in suite X is a hidden time bomb.

Unit Tests

Fast Feedback on Small Logic

✓

One concept per test

Arrange → Act → Assert

Each test should verify one behaviour. If you find yourself writing "and also..." in a test name, split it. Readable test names act as documentation: it_returns_404_when_user_not_found.

✓

Test behaviour, not implementation

Tests that know how the code is implemented break when you refactor — even if behaviour is preserved. Test inputs and outputs. Don't test private methods, internal state, or constructor calls.

✗

Don't assert on dates, random values, or time without freezing them

Flaky tests are worse than no tests. Freeze time, seed randomness, mock the clock. A test that fails 5% of the time will be ignored 100% of the time.

✓

Use descriptive, full-sentence test names

Test names are documentation. test_user_with_negative_balance_cannot_withdraw is better than testWithdraw. When a test fails in a report, the name should explain what broke.

Integration Tests

Verifying That Parts Work Together

✓

Test the boundary between your code and the outside world

Your database queries, HTTP clients, file system calls — these are where integration tests live. Verify that your code correctly queries, sends, and receives from real dependencies.

✓

Use real databases in integration tests — not mocks

If you mock the database, you're not testing integration. Use test containers, in-memory databases (for simple cases), or a dedicated test schema. The point is to catch query bugs, constraint violations, and transaction issues.

✗

Don't mock what you own

If you wrote the code, you should test it directly. Mocks hide bugs in the seams between your own modules. Save mocks for third-party services and infrastructure you don't control.

End-to-End

Critical User Journeys, Not Everything

✓

Test the happy path and the one edge case that matters

E2E tests are expensive. Choose the scenarios that represent real user workflows — signup, purchase, login. If a scenario is important enough to have an E2E test, it's important enough to have full coverage below it.

✗

Don't E2E test happy paths that unit and integration tests already cover

If unit tests already verify that a form validates email correctly, an E2E test duplicating that is waste. E2E tests exist to catch integration failures — not to re-verify business logic.

✓

E2E tests must be deterministic

Use realistic test data. Avoid shared state. Never test with production data. An E2E test that fails due to data issues is noise — noise destroys trust in the test suite.

Mocking Philosophy

Controlled Uncertainty

✓

Mock external services, not your own code

Stripe API, Twilio, a downstream microservice — these should be mocked. Your own modules that you own and control should be tested directly or with test-specific implementations.

✗

Don't over-specify mocks

Mocking every method call and every argument creates fragile tests that break on harmless refactors. Mock only what you need to control — verify behaviour at the boundary, not implementation details.

✓

Verify interactions on mocks — but also verify outputs

Asserting that a method was called is useful but not sufficient. Always also assert on the return value or final state. A mock that was called but with wrong arguments passes the interaction check but fails the real purpose.

Coverage

Metrics That Help, Not Hinder

✓

Use coverage to find gaps, not to judge teams

Coverage is a heuristic — it tells you which lines were never visited. It doesn't say whether the tests that visited those lines were meaningful. Use it to find untested branches, not to set a required percentage.

✗

Don't chase 100% coverage — it buys false confidence

100% coverage means every line was executed at least once. It says nothing about whether assertions were correct, whether edge cases were handled, or whether the tests are checking the right things. A poorly written test can achieve 100% coverage while missing a critical bug.

✓

Aim for meaningful coverage of critical paths

Identify the 20% of the codebase that causes 80% of the bugs and incidents. Ensure those paths — payment logic, auth, data mutations — have thorough test coverage. Everything else can be lighter.
