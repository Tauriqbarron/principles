Security

Security Principles

Conventions for building secure software — defence in depth, OWASP awareness, input validation, secrets management, and authentication patterns.

  • Defence
  • OWASP

Security is not a feature you add at the end — it's a property that emerges from every layer of your system being designed with adversarial thinking. These principles apply across the full stack, from the database to the frontend.
Defence in Depth

Never Rely on a Single Security Control

1
Defence — Strategy
Layer your defences — don't rely on one control

Every security control can fail. A firewall without input validation is one bypass away from compromise. Network security without application-level checks is one zero-day away from lateral movement. Stack controls so that failure of any single layer doesn't mean total failure.

Single control — Avoid architecture.drawio 
# ❌ Network perimeter is the only defence
Internet → [Firewall] → [App Server] → [Database]
-- If attacker bypasses the firewall (e.g., via a compromised VPN),
-- there is nothing stopping them from running arbitrary SQL.
-- No input validation. No query parametrisation. No WAF.
Layered controls — Preferred architecture.drawio 
# ✓ Multiple layers: any one failure is caught by the next
Internet → [WAF] → [API Gateway (rate limit)] → [App Server (validation)] → [ORM (parameterised)] → [Database
-- WAF blocks known attack patterns
-- Rate limiting stops credential stuffing
-- App-level validation catches malformed input
-- ORM parameterisation stops SQL injection even if bypassed
-- Database user has minimal privileges
2
Defence — Principle
Apply least privilege at every layer

Every process, user, and service should run with the minimum permissions required to do its job. If a service is compromised, least privilege limits what the attacker can do with it.

Excessive privilege — Avoid docker-compose.yml 
# ❌ Database user has admin privileges
DB_USER=all_apps
DB_PRIVILEGES=ALL PRIVILEGES
# ❌ App runs as root in container
USER root
-- Compromise of the app = database admin.
-- Container escape = host root.
Least privilege — Preferred docker-compose.yml 
# ✓ Each service has only the privileges it needs
DB_USER=app_readonly
DB_PRIVILEGES=SELECT ON orders, users
DB_WRITE_USER=app_writer
DB_WRITE_PRIVILEGES=INSERT, UPDATE, DELETE ON orders
# ✓ App container runs as non-root
USER node  # uid 1000, no sudo, no /etc write
OWASP

Know and Mitigate the OWASP Top 10

1
OWASP — A07:2021
Broken authentication is the most exploited attack surface

Weak credential storage, missing MFA, predictable session tokens, and missing brute-force protections account for the majority of breaches. Treat authentication as the highest-risk code in your system.

Broken auth: 80%+ of breach root causes MFA enforcement Password hashing: Argon2id / bcrypt Rate-limited login endpoints
2
OWASP — A03:2021
Injection is never acceptable — parameterise everything

SQL injection remains one of the most exploited vulnerabilities. It is entirely preventable. Every query that incorporates user input must use parameterised queries — no exceptions, no legacy exceptions.

String concatenation — Avoid user-repo.js 
# ❌ String concatenation — SQL injection wide open
const query = `SELECT * FROM users WHERE email = '${email}'`;
-- Input: ' OR '1'='1
-- Result: SELECT * FROM users WHERE email = '' OR '1'='1'
-- Returns all users.
Parameterised — Preferred user-repo.js 
# ✓ Parameterised query — user input is never interpreted as SQL
const query = 'SELECT * FROM users WHERE email = $1';
const result = await db.query(query, [email]);
-- Input: ' OR '1'='1
-- Result: selects user with literal email address "'; DROP TABLE..."
-- No injection. No data returned.
3
OWASP — A10:2021
Never make server-side requests to user-controlled URLs

SSRF (Server-Side Request Forgery) lets an attacker make your server fetch arbitrary URLs — including internal services like http://169.254.169.254/ (cloud metadata), file:///etc/passwd, or internal APIs behind a firewall.

Raw URL fetch — Avoid webhook.js 
# ❌ URL taken directly from user input — SSRF wide open
app.get('/fetch', async (req, res) => {
  const { url } = req.query;
  const response = await fetch(url);  // fetches ANY URL
  res.json(await response.json());
});
-- Attacker: ?url=http://169.254.169.254/latest/meta-data/
-- Attacker: ?url=file:///etc/passwd
-- Attacker: ?url=http://localhost:5432/
Allowlist + fetch — Preferred webhook.js 
# ✓ URL validated and resolved to a controlled target
const ALLOWED_HOSTS = ['api.github.com', 'hooks.slack.com'];
app.get('/fetch', async (req, res) => {
  const { url } = req.query;
  const parsed = new URL(url);
  if (!ALLOWED_HOSTS.includes(parsed.hostname)) {
    return res.status(400).json({ error: 'Disallowed host' });
  }
  const response = await fetch(url);
  res.json(await response.json());
});
Input Validation

Validate on Entry, Encode on Exit

1
Validation — Rule
Never trust any data source — validate everything

Request bodies, URL parameters, headers, cookies, environment variables, database reads, and third-party API responses — none of them are trusted by default. Every boundary is a place where malicious data can enter. Validate at the trust boundary, not just at the surface.

Trusted assumption — Avoid user-controller.js 
# ❌ Database is trusted — it shouldn't be
app.get('/user/:id', async (req, res) => {
  // ❌ No validation of req.params.id
  const user = await db.query(
    `SELECT * FROM users WHERE id = ${req.params.id}`
  // Another SQL injection vector — now from a "trusted" source
  );
  res.json(user);
});
Validate at boundary — Preferred user-controller.js 
# ✓ Validate at every trust boundary
app.get('/user/:id', async (req, res) => {
  const id = parseInt(req.params.id, 10);
  if (isNaN(id) || id < 1) {
    return res.status(400).json({ error: 'Invalid user ID' });
  }
  const query = 'SELECT * FROM users WHERE id = $1';
  const result = await db.query(query, [id]);
  res.json(result.rows[0]);
});
2
Validation — Approach
Don't use denylists — use allowlists

A denylist tries to block known bad values. An allowlist defines what is known good and rejects everything else. Denylists are a losing battle — attackers will find bypasses. Allowlists make the attack surface explicit and small.

Denylist — Avoid validator.js 
# ❌ Denylist: attacker finds what you didn't think of
const BLOCKED = ['script', 'onerror', 'onload', 'javascript'];
function sanitise(input) {
  for (const term of BLOCKED) {
    if (input.includes(term)) input = input.replace(term, '');
  }
  return input;
}
-- Bypass: <img src=x onerror=alert(1)>
-- Bypass: <scr<script> -- space-encoded, Unicode homoglyphs...
-- There are infinite bypasses for any denylist.
Allowlist — Preferred validator.js 
# ✓ Allowlist: only known-safe values pass
const ALLOWED_ROLES = new Set(['admin', 'editor', 'viewer']);
function validateRole(role) {
  if (!ALLOWED_ROLES.has(role)) {
    throw new ValidationError(`Role '${role}' is not allowed`);
  }
  return role;
}
-- No bypass possible. Anything not explicitly allowed is rejected.
-- Attack surface is the size of the allowlist, nothing more.
Secrets

Never Ship a Secret

1
Secrets — Storage
Secrets do not belong in source code, environment files, or logs

Hardcoded secrets in source code end up in git history — even after deletion. They leak in CI logs, error reports, Slack messages, and screenshots. The only safe place for a secret is a secrets manager: AWS Secrets Manager, Vault, GCP Secret Manager, or 1Password CLI.

Hardcoded secret — Avoid config.js 
# ❌ Secret in source code — in git history forever
const DB_PASSWORD = 'super-secret-password-123';
const STRIPE_KEY = 'sk_live_4ft8a9...';
-- Even after deletion, git history retains the secret.
-- Anyone who ever cloned the repo has the secrets.
-- Appears in git diffs during code review.
-- Appears in CI/CD logs.
Secrets manager — Preferred config.js 
# ✓ Secrets injected at runtime from a secrets manager
import { getSecret } from './secrets-manager';
const config = {
  dbPassword: await getSecret('prod/db/password'),
  stripeKey:    await getSecret('prod/stripe/key'),
};
-- No secrets in source code. No secrets in git history.
-- Secrets rotated via the manager — no code changes needed.
-- Local dev: use .env.local (gitignored). Production: secrets manager.
2
Secrets — Lifecycle
Design for secret rotation without downtime

Every secret should be rotatable without redeploying or restarting the application. Design your auth and database credential systems so that rotation is a no-op event. Short-lived, rotatable credentials limit the blast radius of a leaked secret.

Auth

Authentication and Session Management

1
Auth — Storage
Never store passwords in plaintext — use a purpose-built password hash

bcrypt, Argon2id, and scrypt are designed for password hashing — they are slow by design, making brute-force attacks expensive. MD5, SHA-256, and SHA-512 are fast hashes designed for data integrity, not password storage. They are trivial to brute-force on modern hardware.

Fast hash — Avoid auth.js 
# ❌ SHA-256 is fast — GPU cracks 10B hashes/sec
const hash = crypto
  .createHash('sha256')
  .update(password)
  .digest('hex');
-- Rainbow tables make this instantaneous for short passwords.
-- A single RTX 4090 can try 10 billion SHA-256 per second.
-- "Password123" cracks in milliseconds.
bcrypt / Argon2id — Preferred auth.js 
# ✓ bcrypt — slow by design, configurable work factor
import bcrypt from 'bcrypt';
const hash = await bcrypt.hash(password, 12);  // cost factor: 12 = ~300ms
const match = await bcrypt.compare(password, hash);
-- 12 rounds: a single guess takes ~300ms.
-- 10 billion guesses: ~95 years.
-- Work factor increases with hardware — plan for future increases.
2
Auth — Sessions
Use short-lived, rotating session tokens with server-side validation

Sessions should have a reasonable lifetime — typically 24 hours for most applications. Tokens should be rotated on each authentication event. Every request must validate the session server-side; never trust a token without verification.

Long-lived token — Avoid session.js 
# ❌ Session never expires — stolen token = permanent access
jwt.sign({ userId }, 'secret', {});  // no expiry — permanent until rotated
-- Token stolen in a man-in-the-middle attack = account takeover forever.
-- No way to invalidate without a blacklist.
Short TTL + rotation — Preferred session.js 
# ✓ Short-lived tokens with refresh rotation
jwt.sign(
  { userId, sessionId },
  SECRET,
  { expiresIn: '15m' }   // short-lived access token
);
-- Refresh token rotation: each use issues a new refresh token.
-- Old refresh token is invalidated — replay attacks are blocked.
-- If a refresh token is leaked after rotation, it's already invalid.
3
Auth — MFA
Enforce MFA for all privileged accounts

Passwords alone are not enough for privileged accounts — admin panels, production access, CI/CD systems. TOTP (authenticator apps) and hardware keys (WebAuthn/FIDO2) provide strong second factors. SMS-based OTP is discouraged due to SIM-swap vulnerability.

TOTP: authenticator apps (Authy, 1Password) WebAuthn: hardware keys (YubiKey), biometrics SMS OTP: SIM-swap vulnerable
