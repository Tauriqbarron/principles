Security is not a feature you add at the end — it's a property that emerges from every decision made during design and implementation. These principles apply across any stack or language. They prioritse layered defence, minimal trust, and assuming every input is hostile until proven otherwise.
Defense in Depth

Never Rely on One Layer

✓

Assume every layer can be breached

Networks get scanned. Firewalls get misconfigured. Servers get compromised. Design each layer assuming the ones outside it have already failed. If an attacker gets read access to your database, can they read passwords? If they get code execution, can they move laterally?

✓

Apply controls at each boundary

Validate input at the API layer, not just the frontend. Sanitise at the rendering layer. Enforce authorisation at the service layer. Each trust boundary is an opportunity to stop an attacker — don't concentrate all controls at the outer edge.

✗

Don't rely on security through obscurity

Hidden admin URLs, unpublished API endpoints, obfuscated JavaScript — these slow down casual attackers for minutes. They add nothing against a determined adversary. Design as if your source code is public.

OWASP Mindset

The OWASP Top 10 Is a Starting Point

✓

Know the OWASP Top 10 by heart

Broken Access Control, Cryptographic Failures, Injection, Insecure Design, Security Misconfiguration, Vulnerable Components, Auth Failures, Data Integrity Failures, Logging Failures, SSRF. These categories cover the majority of real-world vulnerabilities.

✓

Threat-model before writing code

STRIDE Attack trees

For significant features, model the threats before implementation. What does the attacker want? What can they control? What assumptions is the code making? Ask these questions in design, not after a breach.

✗

Don't trust third-party components blindly

The average codebase has hundreds of dependencies. Each one is an attack surface. Pin versions, subscribe to security advisories, scan dependencies regularly. A vulnerability in a transitive dependency is still your vulnerability.

Input Validation

All Input Is Hostile Until Proven Otherwise

✓

Validate and sanitise at every trust boundary

Form submissions, API payloads, URL parameters, headers, cookies, uploaded files — all of it. Validation is not optional. Implement it consistently at every entry point, not just the most obvious ones.

✓

Use allowlists, not denylists

It's easier to say what's valid than what's invalid. For structured input, define the acceptable values, formats, and ranges precisely. Denylists miss edge cases — allowlists enforce correctness by default.

✗

Never trust client-side validation alone

Client-side validation is for UX, not security. An attacker can disable JavaScript, craft raw requests, or use a proxy to send anything. Every validation must be enforced server-side.

✓

Context-output-encode

Data must be encoded for its destination. HTML-encode before rendering in HTML. SQL-escape for queries (or better, use parameterised queries). URL-encode for URL parameters. Shell-escape before passing to a command shell. Wrong encoding is how XSS and injection happen.

Secrets Management

Never in Code, Never in Logs

✓

Store secrets in environment variables or a vault

ENV vars HashiCorp Vault AWS Secrets Manager

Secrets belong in a secrets manager, injected at runtime. They should never appear in source code, container images, config files committed to git, or log streams.

✗

Never commit secrets — scan for them

Use a pre-commit hook or CI step with git-secrets, trufflehog, or similar. A secret in git is a breach — assume it's compromised the moment it's committed, even if you later remove it.

✓

Rotate secrets regularly and after every suspected compromise

Rotation limits the blast radius of a leaked credential. Build systems that support rotation without downtime — key rotation should be a routine operation, not an emergency.

Auth & Sessions

Identity Is the Perimeter

✓

Hash passwords with a purpose-built algorithm

bcrypt argon2 scrypt

Never use MD5, SHA1, or plain SHA-256 for passwords. Use bcrypt, argon2, or scrypt — they are designed to be slow against brute-force attacks. Hash with a per-user salt.

✓

Enforce authorisation at every request — not just authentication

Authentication answers "who are you?". Authorisation answers "are you allowed to do this?". A logged-in user can still attempt actions on resources they don't own. Every mutation must check that the authenticated identity has permission.

✗

Don't use predictable or sequential session IDs

Session IDs must be unguessable. Use cryptographically secure random generators. Never encode meaningful data in the session identifier — it's opaque to the client by design.

✓

Set secure cookie attributes

HttpOnly Secure SameSite=Strict

Auth tokens in cookies require HttpOnly (no JS access), Secure (HTTPS only), and SameSite to prevent CSRF and XSS token theft.

Secure Defaults

Make the Secure Choice the Easy Choice

✓

Default to least privilege

Every process, user, and system should run with the minimum permissions it needs. Database accounts used by web apps should not be database admins. CI pipelines should not have production write access unless necessary.

✓

Fail securely — deny by default

When something goes wrong — an exception, a missing config, an unknown input — the safe behaviour should be to deny. Don't fall back to permissive modes on error. A failing closed system is safer than a failing open one.

✗

Don't skip TLS in non-production environments

Testing with plain HTTP in staging teaches bad habits and creates security debt. If your app works only over plain HTTP, it will be deployed with plain HTTP. Use valid certificates everywhere — Let's Encrypt is free.

✓

Log security events — but never log secrets or credentials

Auth failures, privilege escalations, admin actions, and data access should be logged. But never log passwords, tokens, API keys, or full PII. Use structured logs with a redaction step in your logging pipeline.
