Architecture

Architecture Principles

Conventions for structuring software systems — monolith vs microservices, event-driven architecture, CQRS, and clean architecture layers.

  • Monolith
  • Microservices
  • Event-Driven
  • CQRS
  • Clean Architecture
  • Distributed
Architecture is the set of decisions that are hard to change. Choosing between a monolith and microservices, how to handle distribution, where to draw service boundaries — these decisions have compounding effects. Make them deliberately, understand the trade-offs, and prefer the simplest architecture that meets your current needs.
Monolith

Start Simple — The Monolith Is Not a Mistake

1
Monolith — Decision
Default to a monolith. Decompose only when you have a specific, evidenced problem

A well-structured monolith is easier to build, test, deploy, and debug than a distributed system. The operational burden of microservices — network latency, partial failures, distributed tracing, service discovery — only pays off when you genuinely need what microservices offer: independent scaling, multiple technology stacks, or team boundaries along service lines.

Premature split — Avoidarchitecture.svg
# ❌ Team of 3, early product — microservices overhead
[API Gateway] → [Auth Svc] → [Order Svc] → [Payment Svc]
             → [User Svc] → [Notify Svc] → [Inventory Svc]
-- 7 services to deploy, monitor, trace, and debug.
-- Cross-service refactors require 7 coordinated PRs.
-- Team of 3 spends more time on infrastructure than product.
Well-structured monolith — Preferredarchitecture.svg
# ✓ Single deploy, clear module boundaries
[App] → modules/auth, orders, payments, users, notifications
-- One CI pipeline, one deployment, one log stream.
-- Module boundaries mirror service boundaries — when you DO need to
-- split, the seams are already there.
-- Debugging: one process, one breakpoint, full call stack.
2
Monolith — Discipline
Enforce module boundaries within the monolith as strictly as service boundaries

A monolith without enforced boundaries becomes a big ball of mud — every module depends on every other. Use package namespaces, dependency inversion, and architecture tests (e.g., ArchUnit) to keep modules isolated. When you eventually need to split, clean seams will already exist.

Circular deps — Avoidmodule-deps.png
# ❌ Modules depend freely — entangled call graph
auth → orders → payments → notifications → auth (cycle!)
users → auth → orders → users (cycle!)
-- Every change requires understanding the entire codebase.
-- Testing any module requires the full application context.
-- Extracting a service means untangling years of cross-dependencies.
Layered deps — Preferredmodule-deps.png
# ✓ Strict dependency direction — no cycles
controllers → services → repositories → database
domain ← services ← controllers
-- Each module has exactly one upstream consumer.
-- Cross-cutting concerns injected via interfaces.
-- New module: follows the same pattern, automatically fits.
Microservices

Split When You're Ready for the Operational Cost

1
Microservices — Rule
Services are split along business capabilities, not technical layers

A service called "user-service" that only manages user data is not a business capability — it's a data layer with a name. A service called "identity-service" that handles authentication, authorisation, sessions, and identity verification is a business capability. Split along the lines of what the business does, not what the code does.

Layer split — Avoidservices-bad.svg
# ❌ Splitting by layer — the "Nanoservices" anti-pattern
[UserController] → [UserService] → [UserRepo]    → [User DB]
[AuthController] → [AuthService] → [AuthRepo]    → [Auth DB]
[OrderController] → [OrderService] → [OrderRepo] → [Order DB]
-- Every business operation spans 3 services and 3 databases.
-- Distributed transaction everywhere.
-- No service can function without the other two.
Capability split — Preferredservices-good.svg
# ✓ Split along business capability — each owns its domain
[Identity Service] — auth, sessions, MFA, OAuth
[Order Service]     — orders, checkout, pricing, promotions
[User Service]     — profiles, preferences, avatar, settings
-- Each service encapsulates one domain.
-- A service can fail without taking down the entire product.
-- Teams own their domain end-to-end.
2
Microservices — Goal
Services should be independently deployable and testable

If you can't deploy service A without deploying service B, they are not two services — they are one service with two names. True service independence means independent CI/CD pipelines, independent data stores, and no coordinated rollouts.

Independent CI/CD per service Own database per service No distributed transactions across services
Event-Driven

Events Are Contracts — Design Them Carefully

1
Event-Driven — Rule
Never publish internal state changes — publish business events

Publishing user.email = 'new@example.com' is a technical state change. Publishing UserEmailChanged { userId, oldEmail, newEmail, changedAt } is a business event. Consumers don't care that a column was updated — they care that something meaningful happened in the domain.

State change — Avoidevents-bad.json
# ❌ Exposing internal state — tight coupling, no business meaning
{
  "type": "UserUpdated",
  "payload": {
    "id": 42,
    "email": "new@example.com"
  }
}
-- Consumer must know the old value to understand what changed.
-- Renaming the column breaks all consumers.
-- No indication of WHY this happened (edit? import? merge?).
Business event — Preferredevents-good.json
# ✓ Business event — self-describing, semantically meaningful
{
  "type": "UserEmailChanged",
  "payload": {
    "userId": "usr_42",
    "oldEmail": "alice@example.com",
    "newEmail": "new@example.com",
    "changedBy": "usr_11",
    "reason": "user-initiated"
  }
}
-- Consumer knows exactly what happened without querying the source.
-- Schema evolution: add fields, don't rename.
-- Consumers can react to the intent, not the implementation.
2
Event-Driven — Anti-pattern
Don't use events as a synchronous RPC replacement

If a consumer waits for an event to complete a request-response cycle, you have synchronous coupling via a message bus. Events should be fire-and-forget — the producer never knows or cares who consumes it, or when. If you need a response, use a request-response pattern (HTTP, gRPC), not an event.

CQRS

Separate Read Models from Write Models

1
CQRS — Concept
Reads and writes have fundamentally different optimisations — separate them

A data model optimised for writes (normalised, transactional) is rarely optimal for reads (denormalised, aggregated, projected). CQRS allows you to have a write model that enforces invariants and business rules, and a read model that is shaped exactly for the queries your UI needs — with no compromises.

One model — Avoidqueries.sql
# ❌ Same model for reads and writes — forced compromise
SELECT u.name, u.email, COUNT(o.id), SUM(o.total)
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = $1
GROUP BY u.id
-- O(n) join on every user dashboard load.
-- Adding a "last order date" field requires a schema migration and
-- a new query — both risky on a live system.
-- Read model is always a compromise.
CQRS read model — Preferredread-model.sql
# ✓ Read model: pre-joined, pre-aggregated, shaped for the UI
SELECT * FROM user_dashboard WHERE user_id = $1
-- user_dashboard is a materialised view / read model table:
-- name, email, order_count, lifetime_value, last_order_date,
-- loyalty_tier — all pre-computed.
-- UI query: single row fetch, O(1).
-- Adding a new read field: update the projection, no schema change.
2
CQRS — Trade-off
Read models are eventually consistent — design for it

When a write is committed, the read model is updated asynchronously — there is a window where the read is stale. If your use case requires the write to be immediately readable (e.g., "I just submitted a form, let me see my data"), CQRS is the wrong pattern. Use it when stale reads are acceptable — dashboards, analytics, search results.

CQRS is wrong if: immediate read-after-write consistency needed CQRS is right if: dashboard, search, analytics, reporting
Clean Architecture

Dependencies Flow Inward — The Core Owns the Rules

1
Clean Architecture — Rule
Dependencies point toward the domain — never the reverse

The domain layer (entities, value objects, domain events) is the core of your application. It should have zero dependencies on infrastructure — no database, no HTTP client, no framework. Infrastructure details depend on the domain; the domain never depends on infrastructure. This is achieved through interfaces (ports) that the domain defines and infrastructure implements (adapters).

Infrastructure in domain — Avoidorder-service.js
# ❌ Domain depends on infrastructure — untestable, fragile
class OrderService {
  async placeOrder(itemId: number, userId: number) {
    const db = new PostgresDB(config);  // domain owns DB concern
    const email = new SendGridClient(key);  // domain owns email concern
    const inventory = new RestClient(baseUrl);  // domain owns HTTP concern
    // ... business logic mixed with I/O
  }
-- OrderService cannot be unit tested without a real Postgres DB.
-- Changing the email provider requires changing the domain layer.
-- Business rules are hidden among infrastructure concerns.
Interface inversion — Preferredorder-service.ts
# ✓ Domain defines the interface; infrastructure implements it
// domain/ports.ts — interface owned by domain
interface OrderRepository { save(o: Order): Promise<Order> }
interface EmailService { send(t: Email): Promise<void> }
interface InventoryService { check(itemId: number): Promise<boolean> }
// domain/order-service.ts — depends only on interfaces
class OrderService {
  constructor(
    private repo: OrderRepository,
    private email: EmailService,
    private inventory: InventoryService
  ) {}
-- All dependencies injected — fully unit testable.
-- Changing email provider: implement new EmailService, don't touch domain.
-- Business rules are isolated and independently testable.
2
Clean Architecture — Scope
Each use case is a single, complete transaction in the domain layer

A use case (or application service) coordinates the domain objects to accomplish one business action. It should be thin — it doesn't contain business rules, it orchestrates them. A use case should be small enough to read in one sitting and describe in one sentence.

Distributed Systems

The Fallacies of Distributed Computing Are Not Suggestions

1
Distributed — Reality
Network latency is non-zero. Bandwidth is finite. Networks fail.

The 8 fallacies of distributed computing: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology doesn't change, there is one administrator, transport cost is zero, the network is homogeneous. Every distributed system failure is in some sense a fallacy being violated.

Assume reliability — Avoidpayment.js
# ❌ Network call with no failure handling — brittle
const response = await fetch('http://payment-svc/charge', {
  method: 'POST',
  body: JSON.stringify({ amount })
});
-- If payment-svc is down, this throws an unhandled exception.
-- No timeout. No circuit breaker. No retry.
-- A single downstream failure takes down the entire request.
Graceful degradation — Preferredpayment.js
# ✓ Timeout, retry, circuit breaker — graceful degradation
const response = await fetch('http://payment-svc/charge', {
  method: 'POST',
  body: JSON.stringify({ amount }),
  signal: AbortSignal.timeout(3000)  // 3s timeout
}).catch(err => {
  if (err.name === 'TimeoutError') {
    throw new PaymentTimeoutError();
  }
  throw err;
});
-- Timeout prevents indefinite blocking.
-- Circuit breaker prevents hammering a failing service.
-- Error is domain-aware — PaymentTimeoutError, not a raw fetch error.
2
Distributed — Theorem
Understand the CAP theorem — consistency vs availability is a real trade-off

In the presence of a network partition, you must choose between consistency and availability. You cannot have both. Most distributed databases allow you to tune this per operation — understanding which operations require strong consistency (e.g., financial transactions) and which can tolerate eventual consistency (e.g., social media likes) is a fundamental architectural decision.

Strong consistency: financial transactions, inventory Eventual consistency: likes, views, search indexes, caches
