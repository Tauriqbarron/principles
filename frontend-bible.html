The Underlying Philosophy
title: "Frontend Bible" outline: 0 owners: - name: "Pouya Ataei" slack: "U015U81L2AK"
Now that you chose to embark on a real enterprise-level frontend development, this document will serve as the guiding light.

Why does one project within an organization flourish while another project with the same fundamental architectural needs, within the same organization, flounders? Often, the root of the problem is a lack of overarching standard that keeps development on a steady and smooth line.

What we aim to achieve here as a team; is a progressive and collective effort of creating a grade-A software product; the one that we are not afraid to modify and extend; the one that we are not horrified to refactor. This, my child, is the art of software engineering. Our frontend vision is stated here.

This document aims to shed light on fundamental standards that we have defined here at ezyVet. Before getting into actual coding decisions and dos and don’ts, we first need to review our underlying philosophy towards development.

Here are 17 philosophies that we stick to at any cost (heavily inspired by the Zen of Python):

  1. Explicit is better than implicit.
  2. Simple is better than complex.
  3. Complex is better than complicated.
  4. Flat is better than nested.
  5. Indeed, the ratio of time spent reading versus writing is well over 10 to 1. We are constantly reading old code as part of the effort to write new code. ...
  6. Therefore, making it easy to read makes it easier to write.
  7. It is not enough for code to work, when the codes works, you start engineering!
  8. A long descriptive name is better than a short enigmatic name.
  9. You should name a variable using the same care with which you name a first-born child.
  10. Clean code always looks like it was written by someone who cares.
  11. The first rule of functions is that they should be small. The second rule of functions is that they should be smaller than that.
  12. Special cases aren't special enough to break the rules.
  13. Errors should never pass silently. Unless explicitly silenced.
  14. In the face of ambiguity, refuse the temptation to guess.
  15. There should be one-- and preferably only one --obvious way to do it.
  16. Now is better than never.
  17. If the implementation is hard to explain, it's a bad idea.
  18. If the implementation is easy to explain, it may be a good idea.

Folder structure

Code organization is a critical matter. It is essential to modularise pieces of functionality and abstract out only what is necessary. Encapsulation and abstraction are very basic matters but often neglected.

We do follow this folder structure for components:

Thinking about it this way. Component A (module A) needs to encapsulate all the dependencies it has in its own folder. However, if we had a util or type that we can reuse across components, we will place it in the higher folder structure, so it can be reused across the project.

Every module should only have one index file. So your sub-components do not need to be moduled themselves, this is to keep the folder structure as flat as possible.

In simpler terms, only ad-hoc dependencies of a module will be encapsulated in its folder (things that cannot be reused by other modules). The index file is the gateway that abstracts out this module.

So the gotcha here is that, if you had several sub-components inside your component, you should not create a type, test, or other folders for them, because they are not a module by themselves! they’re just ad-hoc sub-components of your module.

If you had a high-level reusable component, types, utils, or a graph query, it should be placed in the highest level of folder structure. An example is as following:

If you have several utils for one component. Define an index.ts for utils and export everything in one place. This helps you save an import when you have to import several utils into your component.

Here is an example:

Tip

If you do have test utils and mocks that are shared among several modules, place your test utils inside the general high-level tests folder under utils and place your mocks under the same folder under mockData.

The same rule applies for ad-hoc inside module mocks and utils. Ideally you don’t have a test util that you only use for one module, but if that was the case there will be a sub-folder under test folder, called utils, for mocks, mockData.

Keep components clean! like really clean
Any fool can write code that a computer can understand. Good programmers write code that humans can understand.
No component should be more than 150 lines! This is very important for the ezyVet frontend team. You should never have your types in your component, you should never declare styles in the component, you should never have another component defined in the same file, you should not have handlers defined in a component, you should abstract out your lifecycle logic to a hook and take it out. One file just exports one component and that’s it.

Here is an example of a clean component:

Example
// Libraries
import React from "react";

// Components
import { SortableContainer } from "../components/SortableContainer";
import { MetaRecordsDescription } from "../components/MetaRecordsDescription";

// Utils
import { configAggregator } from "../utils/helpers/configAggregator";

// Types
import { MetaRecordsFormProps } from "../types/MetaRecordsFormTypes";
import { ExtendedInvoiceLine } from "../../records/redux/selectors/invoice/getTableConfig";

export const MetaRecordsForm = ({
  defaultColumnConfig,
  columnMetaConfig,
}: MetaRecordsFormProps<ExtendedInvoiceLine>) => {
  return (
    <>
      <MetaRecordsDescription />
      <SortableContainer
        aggregatedConfig={configAggregator(
          defaultColumnConfig,
          columnMetaConfig
        )}
      ></SortableContainer>
    </>
  );
};
5
Module exporting

Here in ezyVet we only do named exports. Please avoid default exports at any costs, _unless it is a lazy loaded component_ (see clause 6). We also use arrow functions to avoid scoping issues.

Here is a good example:

This has several benefits:

  1. Increased discoverability: Depending on your IDE, discoverability can be poor for default exports. You cannot explore a module with IntelliSense to see if it has a default export or not.
  1. CommonJS interop: With default there experience is bad for commonJS users who have to const {default} = require('module/foo'); instead of const {Foo} = require('module/foo'). You will most likely want to rename the default export to something else when you import it. This adds more semantic.
  1. TypeScript auto-import: Auto import quick-fix works better. You use Foo and auto import will write down import { Foo } from "./foo"; cause it's a well-defined name exported from a module. Some tools out there will try to magic read and _infer_ a name for a default export but magic is flaky.
  1. Re-exporting: Re-exporting is common for the root index file in npm packages, and forces you to name the default export manually e.g. export { default as Foo } from "./foo"; (with default) vs. export * from "./foo" (with named exports).
  1. Better tree-shaking: named exports do define a much more confined boundary, this helps webpack tree-shaking algorithm.
  1. Explicit is better than implicit: named exports are much more explicit than default ones. The scope of these exports are also confined and boundaries are better defined.
Example
export const MetaRecordsForm = ({
  defaultColumnConfig,
  columnMetaConfig,
}: MetaRecordsFormProps<ExtendedInvoiceLine>) => {

Lazy loaded components
Lazy loading or on-demand loading reduces page weight, allowing for a quicker page load time. Hence components that are not visible on initial load can be lazy loaded using React.lazy and suspense.

Today, React.lazy does not allow dynamic imports or named imports. Due to this current limitation, we will default export the components that are lazy-loaded.

Example:

Example
// Components
import { SuspenseWrapper } from "../utils/Suspense/SuspenseWrapper";
const LazyLoadedComponent = lazy(() =>
  import("./components/LazyLoadedComponent")
);

export const SampleComponent = ({
  title,
  showDetails,
}: SampleComponentProps) => {
  return (
    <>
      <TitleComponent title={title} />
      <SuspenseWrapper>
        <LazyLoadedComponent showDetails={showDetails} />
      </SuspenseWrapper>
    </>
  );
};
7
Our approach to styling

As of Feb 2021, our only approach to styling is through Styled Components (SC). SC has so many things figured out for us such as class names, CSS in JS, performance and conditional styling. This means we don't have to use any naming methodology such as BEM (Block, Element, Modifier). Aside from that, we get the benefit of automatic critical CSS. Please try to reuse our common SCs in the styles folder, as they are highly configurable.

Avoid using Material at any cost, unless you directly discuss the issue with the frontend tech lead and get approval. If you utilized Material UI grids, buttons, chips, dropdowns or anything else, you will be asked to replace them all with SC.

Always functional and compositional

Keep all functions pure. If you don’t know what a pure function is, just Google it. Please do not call anything from the general scope of your component into your helper functions.

Bad Example: Good Example:

If you paid attention you’ll see that in the second code block we just pass the function as a parameter, which means giving the same parameter we expect the same output. On the other hand, in the first example, we are just invoking another function from the scope of the component (a higher-level scope); this is a road to perdition and is definitely not in line with functional programming principles.

It’s best if you read about Category theory, nomiads, and the foundation of functional programming. We do suggest Frontend Masters courses. If you were really keen, talk to the frontend tech lead for access to the website.

Avoid — Anti-pattern
const component = () => {
    function a = (param) => console.log(`I’m function A with ${param} `)
    function b = ( ) => {
        a('yo')
        console.log('I’m function')
    }
    b()
    return <div>test</div>
}
Prefer — Best Practice
const component = () => {
    function a = (param) => console.log(`I’m function A with ${param} `)
    function b = (helperLogic) => {
        helperLogic('yo')
        console.log('I’m function')
    }
    b(a)
    return <div>test</div>
}
9
Favor hooks over HOCs and wrappers

Avoid higher-order components or heavily wrapped components. They tend to confuse developers and add a lot of boilerplates as well. Aim for hooks. Hooks are the de facto standard and the most functional approach you can have. mapStateToProps, MapDispatchToProps and all of that are not acceptable. Instead try useStore and useDispatch from the library react-redux. Eventually Redux will get deprecated in this project, but for now, we keep it clean.

You should only use HOCs or render props pattern if that was the best choice and you could not achieve reuse otherwise.

Our design system

In ezyVet we follow the principles of atomic design. Take for instance the periodic table of elements; we know that all matter is comprised of atoms; these atoms bond together and create molecules; molecules in turn bond together and create organisms, organisms in turn bond together to create complex or super organisms, and ultimately the whole universe.

In the same vein, interfaces are made up of small matters. This implies that we can break down UI components into their fundamental building blocks. Atomic design is a methodology for creating design systems. There are five distinct levels in atomic design:

  1. Atoms
  2. Molecules
  3. Organisms
  4. Templates
  5. Pages

Atoms

Atoms are basic building blocks of a matter, in the frontend sense they are the HTML elements such as form, label, input, etc...

Atoms can be fonts, color pallets as well.

Like atoms in nature, these elements are fairly abstract and are not very useful in silos.

Molecules

Molecules emerge when atoms get together and bond. Imagine if you had a title and an input and a button and you put them all together, this emerges into something that users can interact with. Building up molecules from atoms encourages the mentality of 'do one thing and do it well'.

While molecules can be complex, as a rule of thumb they are relatively simple combinations of atoms built for reuse.

Organisms

Organisms are made up of several molecules. Organisms are groups of molecules joined together to form a relatively complex, distinct section of an interface. One good example is a navigation pane. templates.

Templates

Templates are made up of few organisms. Templates consist mostly of groups of organisms stitched together to form pages. One good example is the sidebar, the main section of a page, or a footer.

Pages

Pages are the highest level of fidelity and because they're the most tangible, it's typically where most people in the process spend most of their time and what most reviews revolve around. I think you don't need an example, do you? :P

Wanna read more? there you go → (https://bradfrost.com/blog/post/atomic-web-design/#organisms)

11
Destructing

Always destruct the desired properties from the objects. Why? Destructuring saves you from creating temporary references for those properties, and from repetitive access to the object. Repeating object access creates more repetitive code, requires more reading, and creates more opportunities for mistakes. Destructuring objects also provide a single site of the definition of the object structure that is used in the block, rather than requiring reading the entire block to determine what is used.

Bad Good Best
Avoid — Anti-pattern
function getFullName(user) {
  const firstName = user.firstName;
  const lastName = user.lastName;

  return `${firstName} ${lastName}`;
}
Prefer — Best Practice
function getFullName(user) {
  const { firstName, lastName } = user;
  return `${firstName} ${lastName}`;
}
Example
function getFullName({ firstName, lastName }) {
  return `${firstName} ${lastName}`;
}
12
Grid over flex

Whereas Flex layout is useful in simple scenarios, it is a bad choice for complicated layouts. Governing horizontal and vertical space is a known issue when it comes to flex. Favor grid layout in complicated or even seemingly complicated or even normal cases.

Only go for Flex layout if you found Grid layout overkill or if you have a very simplistic UI.

Iteration

As engineers we always end up iterating over something. When you had to access properties of your data structure quite frequently favour Maps, if you wanted to keep unique set of values, favour Sets, if you went with objects or array, try to iterate them in the fastest way possible.

The benchmark below can help you understand what's fastest.

!Iteration Performance

Another gotcha is that sometimes if you’re filtering out properties or searching for a specific property, you may use a language constructs that does not stop the iteration even after filtering or finding the value. One good example is forEach(). As of December 2021, there is no way to stop or break a forEach() loop other than by throwing an exception. If you need such behavior, the forEach() method is the wrong tool.

Early termination may be accomplished with:

  • A simple for loop
  • A for...of / for...in loops
  • Array.prototype.every()
  • Array.prototype.some()
  • Array.prototype.find()
  • Array.prototype.findIndex()
  • Array methods: every(), some(), find(), and findIndex() test the array elements with a predicate returning a truthy value to determine if further iteration is required.

Avoid unnecessary ternary statements

Here we focus on declarative code and less boilerplate. If you can achieve something by writing less code, then that’s desirable.

Bad Good
Avoid — Anti-pattern
const foo = a ? a : b;
const bar = c ? true : false;
const baz = c ? false : true;
Prefer — Best Practice
const foo = a || b;
const bar = !!c;
const baz = !c;
15
Be wary of State my child

State, in computer science sense, and in its all flavors is a dangerous thing. Keeping it consistent is a headache, it’s prone to failures, it’s prone to bugs, and it can turn into an abomination easily. I personally think that state management is one of the hardest things to do in the Frontend space.

For that sake, make sure that you make as many dumb stateless components as you can, and delegate state management to only a few components. Container pattern and stateReducer are a few good patterns to look into.

Introduce state to components with caution.

16
Stick to the single responsibility

The Single Responsibility Principle (SRP) states that a class or module should have one, and only one, the reason to change. Please do not create a helper function that does the checks, mutation, and lots of other things as well. Do not try to handle two data types, don’t create a function that handles objects and arrays.

Testing

As of April 2021, we do only accept tests written in react-test-utils. Please make sure the tests are not very expensive and take every opportunity to make tests run in concurrent mode. If you're not familiar with concurrent mode in Jest, please do a quick Googling.

When writing any tests, we want our failures to be as human-readable as possible so that we can diagnose and solve the issue immediately.

In frameworks like Protractor and Jasmine, blocks of tests are written in a pattern of "describe/it". These two lines are crucial elements in improving your testing workflow. Jest is inspired by the same ideology.

Thus when you're writing your tests, please make sure that the describe and test produce a cohesive error message.

How to target DOM elements in my tests? what is the best selector?

We try to only expose methods and utilities that encourage you to write tests that closely resemble how your web pages are used.

Utilities are included in this project based on the following guiding principles:

  1. If it relates to rendering components, then it should deal with DOM nodes rather than component instances, and it should not encourage dealing with component instances.
  2. It should be generally useful for testing the application components in the way the user would use it. We *are* making some trade-offs here because we're using a computer and often a simulated browser environment, but in general, utilities should encourage tests that use the components the way they're intended to be used.
  3. Utility implementations and APIs should be simple and flexible.

Based on that, your test should resemble how users interact with your code (component, page, etc.) as much as possible.

With this in mind, we recommend this order of priority:

  1. Queries Accessible to Everyone Queries that reflect the experience of visual/mouse users as well as those that use assistive technology.
  • getByRole: This can be used to query every element that is exposed in the accessibility tree. With the name option you can filter the returned elements by their accessible name. This should be your top preference for just about everything. There's not much you can't get with this (if you can't, it's possible your UI is inaccessible). Most often, this will be used with the name option like so: getByRole('button', {name: /submit/i}). Check the list of roles.
  • getByLabelText: This method is really good for form fields. When navigating through a website form, users find elements using label text. This method emulates that behavior, so it should be your top preference.
  • getByPlaceholderText: A placeholder is not a substitute for a label. But if that's all you have, then it's better than alternatives.
  • getByText: Outside of forms, text content is the main way users find elements. This method can be used to find non-interactive elements (like divs, spans, and paragraphs).
  • getByDisplayValue: The current value of a form element can be useful when navigating a page with filled-in values.
  1. Semantic Queries HTML5 and ARIA compliant selectors. Note that the user experience of interacting with these attributes varies greatly across browsers and assistive technology.
  • getByAltText: If your element is one which supports alt text (img, area, input, and any custom element), then you can use this to find that element.
  • getByTitle: The title attribute is not consistently read by screenreaders, and is not visible by default for sighted users
  1. Test IDs - getByTestId: The user cannot see (or hear) these, so this is only recommended for cases where you can't match by role or text or it doesn't make sense (e.g. the text is dynamic).
19
Small commits

Small commits are industrial best practices, and that's for several reasons;

  1. Getting early feedback from tools which encourages the idea of continuous integration and improvement
  2. Reverting a mistake is far easier
  3. Bugs and issues can be identified and easily removed
  4. If you're on the wrong architectural path, you can prevent it at an earlier stage rather waiting for the whole thing to work and complete
  5. It improves statistics
  6. It also promotes better commit message! (since small commits are usually more focused)

Many people are challenged to achieve this, but it's not that challenging. Think about your units of code and how you can segregate them, you can then push a unit of code with tests.

This is currently setup as a pre-push hook so if you go above 400 you won't be able to push. If you hack around this, the tech lead would know, thus I encourage you to respect this.

20
Reusability

Try to eliminate any ad-hoc component that you have to write. Either use what we have created or create something that people can reuse in the future. This is how we understand the "forest" of an architecture, without getting mired in understanding individual "trees." Context, API calls, containers, labels, these all should be reusable.

21

Frontend is literally the user's computer which can come in varying resources. You should aim for the least possible resource consumption. Stale props and Zombie Children

One of the most difficult aspects of React Redux's implementation is ensuring that if your mapStateToProps function is defined as (state, ownProps), it will be called with the "latest" props every time. Up through version 4, there were recurring bugs reported involving edge case situations, such as errors thrown from a mapState function for a list item whose data had just been deleted.

Starting with version 5, React Redux has attempted to guarantee that consistency with ownProps. In version 7, that is implemented using a custom Subscription class internally in connect(), which forms a nested hierarchy. This ensures that connected components lower in the tree will only receive store update notifications once the nearest connected ancestor has been updated.

However, this relies on each connect() instance overriding part of the internal React context, supplying its own unique Subscription instance to form that nesting, and rendering the with that new context value.

With hooks, there is no way to render a context provider, which means there's also no nested hierarchy of subscriptions. Because of this, the "stale props" and "zombie child" issues may potentially re-occur in an app that relies on using hooks instead of connect().

Specifically, "stale props" means any case where:

  • a selector function relies on this component's props to extract data
  • a parent component *would* re-render and pass down new props as a result of an action
  • but this component's selector function executes before this component has had a chance to re-render with those new props

Depending on what props were used and what the current store state is, this *may* result in incorrect data being returned from the selector, or even an error being thrown.

"Zombie child" refers specifically to the case where:

  • Multiple nested connected components are mounted in a first pass, causing a child component to subscribe to the store before its parent
  • An action is dispatched that deletes data from the store, such as a todo item
  • The parent component *would* stop rendering that child as a result
  • However, because the child subscribed first, its subscription runs before the parent stops rendering it. When it reads a value from the store based on props, that data no longer exists, and if the extraction logic is not careful, this may result in an error being thrown.
useSelector() tries to deal with this by catching all errors that are thrown when the selector is executed due to a store update (but not when it is executed during rendering). When an error occurs, the component will be forced to render, at which point the selector is executed again. This works as long as the selector is a pure function and you do not depend on the selector throwing errors.

If you prefer to deal with this issue yourself, here are some possible options for avoiding these problems altogether with useSelector():

  • Don't rely on props in your selector function for extracting data
  • In cases where you do rely on props in your selector function *and* those props may change over time, *or* the data you're extracting may be based on items that can be deleted, try writing the selector functions defensively. Don't just reach straight into state.todos[props.id].name - read state.todos[props.id] first, and verify that it exists before trying to read todo.name.
  • Because connect() adds the necessary Subscription to the context provider and delays evaluating child subscriptions until the connected component has re-rendered, putting a connected component in the component tree just above the component using useSelector() will prevent these issues as long as the connected component gets re-rendered due to the same store update as the hooks component.

I've tried to standardise this in the past, but it's a bit difficult. There is no formal method to achieve this, but there maybe some standards we can pick up to make this better.

We can think about the following ways to abstract code in JS:

  • Function composition: This involves combining two or more functions to create a new function. For example, you might have a function that converts a string to lowercase and another function that removes whitespace. By composing these functions together, you can create a new function that takes a string, converts it to lowercase, and removes whitespace all in one step.
  • Currying: This involves breaking down a function that takes multiple arguments into a series of functions that each take a single argument. For example, instead of a function that takes two numbers and adds them together, you might create a series of functions that each take a single number and return a new function that adds that number to the original input. This allows you to create more flexible and reusable functions.
  • Higher-order functions: These are functions that take other functions as arguments or return functions as their result. This allows you to create functions that are more flexible and reusable, as you can pass in different functions depending on the context or requirements.
  • Partial application: This involves creating a new function by fixing some of the arguments of an existing function. For example, you might have a function that takes three arguments, but you only want to provide the first two. By partially applying the function, you can create a new function that takes only two arguments and has the third argument pre-filled with a default value.
  • Regular functions: Abstracts a responsibiliy, so as to aligns with unix philosophy. A function that does one thing, and does it right!... so the fact of the matter is: does that function really do anything? or is it just spawned to call another function? so does calling other functions a responsibiliy of a function? well, no! and that's where the confusion come from. We need some sort of agency associated to functions, or if it's composition, we should use some of the other abstraction methods listed above. But what if it's just a transient container? well Anonymous functions may suit..
  • Anonymous functions: These are functions that don't have a name and are defined inline. They are useful for creating short, one-off functions that don't need to be reused elsewhere in the code. To curry or not to curry!

Currying is a technique in functional programming that can be quite useful in some contexts, but it's not without its caveats. Here's an expansion on the argument against over-reliance on currying:

  1. Performance Overhead:
  • Extra Closures: Every curried function introduces an additional closure. Closures have an associated memory and performance overhead because they maintain a reference to their containing environment. In languages or environments where closures are expensive, this can be a significant issue.
  • Garbage Collection: Closures can hold onto memory longer than expected due to their references to external variables. This can lead to increased memory consumption, and if not managed properly, potential memory leaks.
  1. Increased Complexity:
  • Cyclomatic Complexity: Currying can increase the cyclomatic complexity of a function, making it harder to test comprehensively. Each curried call adds a new potential path through the code.
  • Readability: For developers who are not familiar with currying or come from non-functional backgrounds, reading and understanding curried functions can be confusing. This can slow down development, increase the learning curve, and lead to bugs.
  • Debugging: Debugging curried functions can be more challenging, especially when trying to trace through multiple layers of curried calls.
  1. Tooling & Stack Traces:
  • Tools like profilers and debuggers can sometimes have difficulty parsing and presenting curried functions in a way that's easy to interpret.
  • Stack traces can become less straightforward, making it harder to pinpoint issues.
  1. Interoperability:
  • In environments where multiple programming styles or paradigms are in use, or where integration with external systems is required, currying can introduce friction. Curried functions may not play nicely with libraries, frameworks, or systems that expect standard function signatures.
  1. Limited Benefit for Many Use Cases:
  • Currying is most beneficial in contexts where partial application and functional composition are frequently used. In many standard applications, the benefits of currying might not be realized, making its overhead a needless complication.
  1. Language & Ecosystem Support:
  • Not all programming languages support currying natively, or they might offer it in a way that introduces additional overhead or limitations. Using currying in such languages can involve workarounds, further complicating the code.
  • Not all libraries or frameworks are designed with currying in mind. Using currying with them might result in unexpected behaviors or incompatibilities.

To clarify, currying can be a powerful tool in the right contexts, especially in functional programming paradigms. However, like all tools, it should be used judiciously and with an understanding of its implications. In some cases, the costs (both in terms of performance and cognitive load) might outweigh the benefits. Therefore I'd encourage you to avoid currying unless you found a very strong case for it.

Using the delete operator is a sin!

The delete operator in JavaScript is used to remove a property from an object. While it can be useful in certain scenarios, there are reasons to be cautious about using it:

  1. Performance Concerns:
  • Deleting properties from objects, especially in large amounts, can lead to performance issues since JavaScript engines optimize the structures of objects based on their shape (a combination of their properties and methods). Removing properties can de-optimize the object and make property accesses slower.
  • In some engines, once a property is deleted, the object is put into "dictionary mode", where property access is slower because it's handled more generically.
  1. Arrays:
  • Using delete on arrays will leave behind undefined values in the places where you've deleted items, making the array sparse. This can lead to unexpected behavior when iterating over the array with methods like forEach or map.
  • Deleting array elements doesn't update the length property of the array. So, if you're relying on the length for any logic, it might introduce bugs.
  1. Inherited Properties
  • If you delete a property on an object that has a similarly named property on its prototype, subsequent references to that property will access the prototype's property. This could lead to unexpected behavior if you're not aware of the prototype's properties.
  1. Non-configurable Properties:
  • If you try to delete non-configurable properties (properties where the configurable attribute is set to false), the delete operator won't have any effect and will not throw an error either (unless you're in strict mode, in which case it will throw a TypeError). This can introduce silent failures.
  1. Clarity and Maintainability:
  • Using the delete operator can make code harder to read and understand, especially for developers who aren't familiar with the nuances of the operator.
  1. Memory Overhead:
  • While you might think that deleting properties would free up memory, the truth is more nuanced. The deleted property might be gone, but the underlying object's structure might still retain some memory overhead, especially if it has been de-optimized due to the delete operation.
  1. Environment Inconsistencies: - In some environments, especially older ones, delete might behave inconsistently. While this is less of an issue with modern browsers and environments, it's still a consideration for broader compatibility.

Given these concerns, instead of deleting properties, you might:

  • Set the property to undefined: This will retain the property key but clear its value.
  • Use Map or Set: If dynamic additions and deletions of keys are a core requirement, consider using Map or Set which have methods designed for adding, retrieving, and deleting data.

Always weigh the pros and cons based on your specific use case and the requirements of your application.

40
Redux reducers should be pure

Dispatching synthetic events or performing any side effects from within a Redux reducer goes against the core principles of Redux architecture. Reducers in Redux are intended to be pure functions, meaning they should only take the current state and an action as inputs and return a new state without causing any side effects. Pure functions are predictable and don't depend on or affect external states.

The purpose of a reducer is solely to compute the new state based on the action received. When you introduce side effects like dispatching events or making API calls within a reducer, you break this principle, making your state management unpredictable and harder to debug.

In Redux, side effects should be handled in middleware or in the action creators themselves, not in reducers. Middleware in Redux, like Redux-Thunk or Redux-Saga, is specifically designed to handle side effects. These tools allow you to dispatch actions, call APIs, and then dispatch further actions based on the API response. By keeping your reducers pure and delegating side effects to middleware or action creators, you maintain a clear and manageable flow of data in your application, making it easier to maintain and debug.

In summary, while you technically can dispatch synthetic events from a reducer, it is not a good practice in the context of Redux's design and architecture principles. It's important to keep reducers pure and handle side effects elsewhere in your application architecture.
