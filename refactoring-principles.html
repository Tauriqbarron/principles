Refactoring

Refactoring Principles

Conventions for when to refactor, the strangler fig pattern, the boy scout rule, and managing technical debt.

  • When to Refactor
  • Strangler Fig
  • Boy Scout Rule
  • Technical Debt
Refactoring is not rewriting. It is the art of improving code without changing its behaviour. Done well, it keeps a codebase liveable as it grows. Done poorly, it introduces bugs under the guise of improvement. The principles here distinguish productive refactoring from risky surgery.
When to Refactor

Refactor When You Need to Understand the Code — Not When You Just Want to

1
When — Anti-pattern
Don't refactor code that works and doesn't need to change — "refactoring" to make it "better" is a risk without a benefit

If the code is correct, tested, understood by the team, and doesn't need to change for the current task — leave it alone. Every refactor is a risk of introducing a bug. The benefit of a refactor must exceed the risk. "This code could be cleaner" is not a reason to refactor — a new feature, a bug fix, or reduced testability are reasons.

Refactor "just because": introduces risk with no immediate benefit Refactor when: adding a feature, fixing a bug, code is untestable, understanding requires it
2
When — Rule
Use the Rule of Three — abstract when you see the same pattern three times

The first time you write something, you write it directly. The second time, you tolerate duplication. The third time, you abstract. Refactoring too early (on the first or second occurrence) creates abstractions for patterns you don't yet understand. Refactoring too late (after ten copies) means a larger migration.

3
When — Signal
Refactor when the code is hard to test — testability is a proxy for design quality

If a piece of code is genuinely hard to write a unit test for, it's usually because of a design problem — tight coupling, implicit dependencies, static state, or side effects buried inside functions. Improving testability almost always improves design. If you find yourself mocking extensively or unable to set up test state, that's a refactoring signal.

Strangler Fig

Incremental Replacement — Don't Rewrite in Place

1
Strangler Fig — Pattern
Grow the new system around the old one — don't replace it in place

The strangler fig pattern: new functionality is built alongside the old system, and traffic is gradually shifted from old to new. When the new system is fully in production and the old system handles zero traffic, it is decommissioned. The key insight: at any point, you have a working, deployable system — either the old one, the new one, or a mix.

Big bang rewrite — Avoidmigration-plan.md
# ❌ In-place rewrite — months of parallel work, one risky switchover
Phase 1 (3 months): Build new system. Old system keeps running.
Phase 2 (1 week):  Switchover — migrate all data, update DNS.
Phase 3: Decommission old system.
-- 3 months of divergence: old system has new features, new system doesn't.
-- Switchover is a single point of failure: everything or nothing.
-- If something goes wrong at switchover, rolling back is a big bang too.
-- Teams lose confidence in the new system without real-world testing.
Strangler fig — Preferredmigration-plan.md
# ✓ Incremental: new system grows around old, one feature at a time
v1.0: Feature flag off. Old system fully in production.
v1.1: New system handles /users. Old handles everything else.
v1.2: New system handles /orders. Old handles /billing.
v1.3: New system handles /billing. Old decommissioned.
-- Every deploy is a working system — old, new, or both.
-- Each feature shift is independently reversible.
-- Real traffic tests the new system incrementally.
-- No big bang switchover risk.
2
Strangler Fig — Mechanism
Use a facade (or feature flag router) at the system boundary to route between old and new

The router/facade decides which system handles each request. As features are migrated, the router is updated. The old system and new system coexist behind the facade, and callers don't know which one is handling their request. This keeps migration invisible to consumers.

Boy Scout Rule

Leave the Code Cleaner Than You Found It

1
Boy Scout — Rule
Every commit should leave the code slightly better — even if just a little

The boy scout rule: "Leave the campground cleaner than you found it." Applied to code: with every change, fix at least one thing that is worse than it should be. Rename a poorly named variable. Extract a long function. Add a missing test. Fix a lint warning. Small, consistent improvements compound over time into a codebase that is genuinely maintainable.

Rename a confusing variable in the code you're touching Extract a function that is doing two things Add a test for the edge case you're about to fix Fix a lint warning — no reason to leave it
2
Boy Scout — Boundary
The boy scout rule applies to the code you're touching — not to untouched code in the same file

Don't use the boy scout rule as a licence to refactor unrelated code in the same PR. A PR that fixes a bug and also refactors three other modules is a PR that is hard to review and hard to revert. Keep refactoring scoped: fix what's necessary for your change, refactor what's genuinely urgent, leave the rest for another day.

⚠ Scope your refactoring to the code directly related to your change. A PR that fixes one bug and touches 15 files for "cleanups" is a red flag in code review.
Technical Debt

Technical Debt Is a Strategic Decision — Make It Consciously

1
Tech Debt — Tracking
Technical debt you can't see accumulates invisibly — track it explicitly

Every shortcut that makes today's work faster but tomorrow's work slower is technical debt. Unlike financial debt, it rarely gets paid back unless explicitly scheduled. Track it in your issue tracker with a "tech-debt" label, an estimate of the cost of fixing it, and a reason for why it was incurred. Untracked technical debt is invisible debt — and it compounds just as dangerously.

Invisible debt — Avoidissues.md
# ❌ Debt hidden in code comments — nobody tracks it
// TODO: this query doesn't use an index, fix later
// FIXME: fragile, relies on implicit global state
-- TODOs in code are never reviewed, prioritised, or scheduled.
-- Over time, the TODO/FIXME count grows and everyone ignores them.
-- No way to measure the debt load on a feature area.
Tracked debt — Preferredproject-board
# ✓ Technical debt tracked as first-class work items
TECH-DEBT-42 | Slow query in /orders — missing index | High | 2 pts
TECH-DEBT-43 | Session relies on in-memory store — won't scale | Med | 5 pts
TECH-DEBT-44 | Hardcoded config — no env var support | Low | 1 pt
-- Debt is reviewed, prioritised, and scheduled like any other work.
-- Quarterly "debt sprint" can make measurable progress.
-- New debt is introduced with an explicit ticket — not silently.
2
Tech Debt — Strategy
Take on debt deliberately — when the interest cost exceeds the borrowing cost, pay it back

Technical debt is not always bad. Sometimes taking a shortcut to ship a feature fast is the right decision — if the cost of the shortcut (in future development time) is less than the opportunity cost of delaying. The key is to understand the interest rate: how much slower does this make every future change in this area? When the interest cost exceeds the value of the shortcut, it's time to pay the debt.
