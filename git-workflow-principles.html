Git Workflow

Git Workflow Principles

Conventions for commit messages, branching strategy, pull request etiquette, and merge vs rebase decisions.

  • Commits
  • Branches
  • Pull Requests
  • Merge vs Rebase
Git is a communication tool as much as a version control system. A well-crafted commit history tells the story of your codebase. A messy one obscures it. These conventions apply to teams of one or one hundred — commit messages are read more often than you think, usually at the worst possible moment.
Commit Messages

Every Commit Tells a Story — Make It Readable

1
Commits — Format
Use conventional commits: type(scope): description

A consistent format makes commit history scannable. fix(auth): handle expired refresh tokens is instantly readable. fixed stuff is not. The type communicates intent (what kind of change), the scope clarifies context (what area), and the description explains the what and why in plain language.

Vague commit — Avoidterminal
# ❌ Meaningless commit messages
git commit -m "fixed it"
git commit -m "updates"
git commit -m "WIP"
git commit -m "asdfgh"
-- Impossible to understand from git log what changed.
-- git blame tells you WHO changed it but not WHY.
-- Bisect is useless when commits have no semantic meaning.
Conventional commit — Preferredterminal
# ✓ Type + scope + clear description
git commit -m "fix(auth): handle expired refresh tokens gracefully"
git commit -m "feat(billing): add metered billing webhook endpoint"
git commit -m "refactor(orders): extract order validation into domain service"
git commit -m "test(api): add integration tests for pagination edge cases"
git commit -m "docs(readme): update local dev setup instructions"
-- git log is now a readable changelog.
-- Conventional changelog tools generate release notes automatically.
-- Scope makes it scannable: all auth changes together.
2
Commits — Size
Commit one logical change at a time — no mixed changes

A commit should contain exactly the changes needed to accomplish one thing — and nothing more. If you fix a bug and refactor a helper in the same commit, they must be reviewed together and reverted together. Separate them. This is what makes git blame useful, bisect precise, and rebase clean.

Mixed commit — Avoidgit log --oneline
# ❌ One commit: refactor, new feature, and bugfix together
a3f9d2b "various changes"
-- What is this commit? You have to read the diff to find out.
-- Reverting the bugfix means losing the refactor.
-- If the feature breaks CI, you can't partially revert.
Atomic commits — Preferredgit log --oneline
# ✓ Each commit is one clean unit of work
a3f9d2b "refactor(orders): extract validation into order-service"
b7e1c4a "fix(orders): handle null shipping address in checkout"
c9d2e8f "feat(orders): add order confirmation email on checkout"
-- Each commit has a single, clear purpose.
-- git revert can undo exactly the change that caused the problem.
-- git blame gives precise history per logical change.
3
Commits — Context
Explain the why, not the what — the diff shows the what

The commit message body should explain the reason for the change — the context, the trade-off considered, the ticket or discussion that motivated it. The diff shows what changed. The message explains why. Future developers (including future you) will thank present you.

No context — Avoidgit log
# ❌ Subject line only — no reasoning
fix(api): return 404 instead of 500 for missing resource
-- WHY return 404 instead of 500? Was a client request? Bug report?
-- What specific case was being mishandled?
-- Without context, a reviewer can't assess the trade-off.
With body — Preferredgit log
# ✓ Subject + body explaining the decision
fix(api): return 404 instead of 500 for missing resource

Previously, missing resources returned 500 Internal Server Error, which
clients handled as generic server failures. Per the API contract (issue #412),
a missing resource is a client error (4xx), not a server error.

Co-authored-by: Alex <alex@example.com>
-- Clear reasoning: issue #412 is referenced.
-- The trade-off is explained: 4xx vs 5xx semantics.
-- Reviewer can verify the decision is correct.
Branching

Branches Are Cheap — Names Should Be Descriptive

1
Branching — Naming
Branch names must communicate intent — not just the ticket number

A branch called feature/42 tells you nothing. A branch called feature/order-confirmation-email tells you exactly what it does. Include context: the type (feature, fix, refactor, docs), the scope (auth, orders, billing), and the specific change.

Unclear name — Avoidgit branch
# ❌ Branch names that require investigation
git branch "fix-1"
git branch "temp"
git branch "alex-working"
git branch "stuff"
-- What does fix-1 fix? Which feature is alex-working on?
-- Stale "temp" branches are never cleaned up.
-- Code review requests are cryptic: "can I get a review on fix-1?"
Descriptive name — Preferredgit branch
# ✓ Branch name = scope + change description
git checkout -b fix/auth/expired-token-graceful-handling
git checkout -b feature/orders/confirmation-email
git checkout -b refactor/billing/metabolism-to-stripe
git checkout -b docs/api/add-pagination-reference
-- git branch -a shows a readable project board.
-- GitHub filters by branch name automatically.
-- PR title pre-fills from branch name.
2
Branching — Lifetime
Short-lived branches — merge or delete within days, not weeks

A branch that lives for more than a week is a merge conflict factory. The longer it lives, the harder it is to merge. If a branch needs more than a few days of work, it's likely too large — break it into smaller increments, merged to main via feature flags if necessary.

Pull Requests

PRs Are Conversations — Write Them to Start One

1
PRs — Size
Keep PRs small — under 400 lines of code changed

A 2,000-line PR takes three hours to review properly. A 200-line PR takes twenty minutes and gets reviewed thoroughly. Review quality is inversely proportional to PR size. If a feature requires more than 400 lines, split it into multiple PRs — or use a feature branch that merges into a feature flag branch before main.

<200 lines: ideal — fast, thorough review <400 lines: acceptable >400 lines: needs split or justification >1000 lines: almost always too large
2
PRs — Description
Write a PR description — don't make reviewers reverse-engineer the diff

A PR description should explain: what changed, why it changed, how to test it, and what to look for in review. Screenshots for UI changes. Migration steps for database changes. Links to the relevant ticket, design doc, or discussion. The diff is the implementation detail — the description is the rationale.

No description — Avoidgithub.com
# ❌ Empty PR description — forces the reviewer to read the diff
Title: "update user model"
Description: (empty)
-- Reviewer must reverse-engineer intent from code.
-- No context for WHY this change was made.
-- No guidance on what to test or focus on.
-- No link to ticket or design discussion.
Full description — Preferredgithub.com
# ✓ PR description with context, testing, and focus areas
## What
Extract order validation from the controller into a domain service,
per the clean architecture principle (issue #88).

## Why
Validation logic was in the HTTP layer — untestable without HTTP.
The domain service is now unit-testable with pure inputs.

## How to test
1. Run existing integration tests — all should pass
2. POST /orders with invalid items → 422 (was 500 before)
3. POST /orders with valid items → 201

## Review focus
- Is the validation logic correctly placed in the domain layer?
- Any edge cases in the validation that I've missed?
Closes #88
3
PRs — Etiquette
Review comments are about the code — not the author

"This is wrong" is not a review comment. "This returns 500 when the resource doesn't exist — should return 404 per our API contract (issue #42)" is. Distinguish between blocking issues (must fix before merge), suggestions (author decides), and nitpicks (optional). Respond to every review comment, even if just to acknowledge it.

Blocking: must fix before merge Suggestion: author's call — acknowledge and explain Nitpick: optional polish — label it "nit"
Merge vs Rebase

Two Ways to Integrate — Choose Deliberately

1
Merge vs Rebase — Decision
Don't merge main into your feature branch as a substitute for rebasing

Merging main into your feature branch (merge commits) keeps the history but creates a messy, non-linear history graph when done repeatedly. Rebasing your feature branch onto main (replay your commits on top of main) keeps a clean, linear history. Both are valid — but pick one strategy and be consistent.

Repeated merge — Avoidgit log --graph
# ❌ Daily merges of main into feature branch — messy history
*   Merge branch 'main' into feature/order-email
|\
| * Merge branch 'main' into feature/order-email  ← yesterday's merge
| |\
| | * Merge branch 'main' into feature/order-email  ← day before
-- Git history is a maze of merge commits, not a readable story.
-- git blame shows commits from other branches bleeding into yours.
-- Impossible to bisect cleanly.
Rebase onto main — Preferredgit log --graph
# ✓ Rebase onto main before merging — linear history
git fetch origin
git rebase origin/main
-- Resolved by rebasing onto latest main.
-- Linear history: one clean line of development.
-- git log --first-parent shows the story without merge noise.
-- Final merge to main is a single fast-forward or merge commit.
2
Rebase — Rule
Never rebase commits that have been pushed to a shared branch

Rebasing rewrites commit history. If other people have checked out your branch, rebasing makes their local history diverge from origin. This creates serious problems for anyone who pulled the old commits. Rebase is safe only for local commits that haven't been shared, or feature branches that are only reviewed — not for shared branches like main, develop, or release.

⚠ If you've already pushed a branch and teammates may have pulled it: use git revert to undo changes instead of rebasing to rewrite them. Or use git merge --no-ff to preserve history without rewriting.
