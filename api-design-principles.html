API Design

API Design Principles

Conventions for building durable, developer-friendly HTTP APIs — REST, GraphQL, versioning, error handling, and pagination patterns.

A well-designed API is a product your consumers love. These principles apply to any HTTP API — whether REST, GraphQL, or a hybrid. They prioritse predictability, discoverability, and resilience.
REST

Resource-Oriented Design

✓

Use nouns for resources, not verbs

Correct GET /users POST /users

Endpoints represent resources. HTTP methods handle actions. Keep URLs clean and predictable.

✗

Never use verbs in URL paths

Wrong GET /getUsers POST /createUser

Verbs belong in HTTP methods, not URLs. Mixing them creates ambiguity and inconsistency.

✓

Use plural nouns consistently

Correct GET /users/{id} DELETE /users/{id}

Consistency beats personal preference. A uniform plural-noun convention means consumers never guess the form.

✓

Respect HTTP semantics

GET POST PUT PATCH DELETE

Use the right method for the job: GET for reading, POST for creating, PUT for full replacement, PATCH for partial updates, DELETE for removal. Return the correct status codes — they carry meaning.

✗

Never use GET for state-changing operations

Wrong GET /users/123/deactivate

GET requests are idempotent and safe — proxies, browsers, and bots all cache them. Side effects belong to POST/PATCH/DELETE.

✓

Structure hierarchies logically

Nested resources should reflect ownership: GET /users/{id}/orders. Limit nesting to 2 levels — deeper hierarchies become brittle.

GraphQL

Schema-First API Design

✓

Define a schema before writing resolvers

A schema is a contract. Design it from the consumer's perspective first. Use query, mutation, and subscription root types clearly.

✓

Use meaningful, consistent naming

camelCase Past tense mutations

Field names in camelCase. Mutations use verb-like names in past tense: createUser, updateUser, deleteUser.

✗

Avoid deeply nested queries

Nesting more than 3-4 levels causes N+1 resolver problems and poor performance. Use batch loading (DataLoader) for related entities.

✓

Always use input types for mutations

Don't use inline arguments in mutations. Define input types — they compose, version, and document better than flattened argument lists.

Versioning

API Evolution

✓

Version in the URL path

/v1/users /v2/users

Most consumers expect version in the URL. It's explicit, bookmarkable, and easy to route. The simplest and most widely understood convention.

✗

Never make breaking changes in a published version

If you must break, increment the version. Add only additive, non-breaking changes to a live version: new optional fields, new endpoints, new enum values.

✓

Sunset old versions gracefully

Announce deprecations in responses (Deprecation header or a deprecated field in the schema). Give consumers time — minimum 6 months before removal.

✗

Don't version everything — only when you break

Not every change needs a version bump. Adding a new field to a response is non-breaking and requires no version change.

Error Handling

Predictable Error Responses

✓

Use a consistent error envelope

code message details

Every error response should follow the same shape: a machine-readable code, a human-readable message, and optional details for field-level validation errors.

✓

Use appropriate HTTP status codes

200 OK 201 Created 400 Bad Request 401 Unauthorized 403 Forbidden 404 Not Found 422 Unprocessable Entity 429 Too Many Requests 500 Internal Server Error

Don't return 200 for errors. Don't return 500 for client mistakes. The status code is the first signal — make it accurate.

✗

Never expose stack traces or internal details in production errors

Internal errors (500s) should log full details server-side and return a generic message to clients. You control what the consumer sees.

✓

Include a request ID in every response

Every request — success or error — should include a unique X-Request-ID header. This makes distributed tracing and support conversations tractable.

Pagination

Cursor & Offset Patterns

✓

Prefer cursor-based pagination for large or frequently updated datasets

after=cursor first=N

Cursors are stable across insertions — page N+1 won't include items that appeared between page loads. Essential for infinite feeds and real-time data.

✓

Use offset pagination only for bounded, user-navigable lists

Appropriate for admin UIs, dropdown searches, or any scenario where jumping to a specific page is a legitimate consumer need.

✓

Always include total count metadata

Paginated responses should include total (or totalCount) and hasNextPage so consumers can render UI correctly.

✗

Don't use page numbers as cursor values

Page numbers break the moment data changes. A cursor should be an opaque, stable value — typically an encoded timestamp or ID, never a computed offset.

Authentication

Auth Patterns

✓

Use Bearer tokens for API authentication

Authorization: Bearer <token>

The standard HTTP auth header. Keep tokens out of URL query strings — they leak via server logs, browser history, and CDN caches.

✓

Distinguish 401 (unauthenticated) from 403 (unauthorised)

401 means no valid credentials. 403 means credentials are valid but lack permission. Conflating them makes debugging hard for consumers.

✗

Don't roll your own auth — use standards

OAuth 2.0, OIDC, JWT. If you're hand-rolling a session mechanism, you're almost certainly missing edge cases. Use battle-tested libraries and protocols.
