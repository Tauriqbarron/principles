API Design

API Design Principles

Conventions for building durable, developer-friendly HTTP APIs — REST, GraphQL, versioning, error handling, and pagination patterns.

  • REST
  • GraphQL
  • Versioning
  • Errors
  • Pagination
  • Auth
A well-designed API is a product your consumers love. These principles apply to any HTTP API — whether REST, GraphQL, or a hybrid. They prioritise predictability, discoverability, and resilience.
REST

Resource-Oriented Design

1
REST — Nouns for Resources
Use nouns, not verbs, in URL paths

Endpoints represent resources. HTTP methods handle actions. Mixing verbs into URLs creates ambiguity and makes your API harder to reason about.

Correct GET /users POST /users
Verb in URL — Avoid requests.http 
# ❌ Actions mixed into paths
GET /getUsers
POST /createUser
POST /updateUserEmail
DELETE /deleteUserById?id=42
Noun + Method — Preferred requests.http 
# ✓ HTTP methods carry the action
GET    /users
POST   /users
PATCH  /users/42
DELETE /users/42
2
REST — Naming Convention
Use plural nouns consistently

Consistency beats personal preference. A uniform plural-noun convention means consumers never have to guess the form of a resource URL.

GET /users/{id} DELETE /users/{id}
Mixed — Avoid requests.http 
# ❌ Inconsistent: singular mixed with plural
GET /user          // singular — why?
GET /users/42/orders // plural
POST /User         // capitalised — inconsistent
DELETE /Users/42   // plural but capitalised
Uniform plural — Preferred requests.http 
# ✓ Consistent: always lowercase plural
GET    /users
GET    /users/42
GET    /users/42/orders
POST   /users
DELETE /users/42
3
REST — HTTP Semantics
Respect HTTP method semantics

Use the right method for the job. GET is safe and idempotent — proxies, browsers, and bots all cache it. Side effects belong to POST/PATCH/DELETE.

Wrong — GET with side effects requests.http 
# ❌ GET must not have side effects
GET /users/123/deactivate
-- Proxies and browsers will cache this.
-- Bots may trigger it. State has changed.
Correct — POST for actions requests.http 
# ✓ POST for actions; correct status codes
POST   /users/123/deactivate
DELETE /users/123
PATCH  /users/123  // partial update
PUT    /users/123  // full replacement
⚠ Caching proxies, CDNs, and browsers all assume GET is safe to cache. A GET that changes state will produce unpredictable behaviour across the internet.
4
REST — URL Structure
Limit URL nesting to two levels

Nested resources reflect ownership. Nesting beyond two levels creates brittle URLs that are painful for consumers and hard to maintain as your domain evolves.

Too deep — Avoid requests.http 
# ❌ Three levels — fragile and verbose
GET /orgs/{org_id}/teams/{team_id}/members/{user_id}/roles
-- Any refactor breaks all consumer integrations.
-- URL length becomes problematic.
Flat or two-level — Preferred requests.http 
# ✓ Flat or two-level maximum
GET /users/{user_id}/orders         // one level — OK
GET /users/{user_id}/orders/{order_id} // two levels — OK
GET /roles/{role_id}                // flat — better for cross-resource access
GraphQL

Schema-First API Design

1
GraphQL — Design
Design the schema before the resolvers

A schema is a contract. Design it from the consumer's perspective first — define query, mutation, and subscription root types clearly.

Resolvers first — Avoid schema.gql 
# ❌ Resolver-driven design — schema is an afterthought
# Resolvers written without a schema contract:
const resolvers = {
  user: () => db.users.findAll(),  // what's the shape?
  // Clients have no contract to rely on.
}
Schema first — Preferred schema.gql 
# ✓ Schema is the contract — written first
type Query {
  user(id: ID!): User
  users(filter: UserFilter, limit: Int): [User!]!
}
type Mutation {
  createUser(input: CreateUserInput!): CreateUserPayload!
  deleteUser(id: ID!): DeleteUserPayload!
}
2
GraphQL — Naming
Use camelCase for fields, past-tense for mutations

Field names in camelCase. Mutations use verb-like names in past tense: createUser, updateOrder, deletePost. This mirrors REST conventions and reads naturally.

Inconsistent naming — Avoid schema.gql 
# ❌ Inconsistent: PascalCase, verbs without tense
type User {
  FirstName: String      // PascalCase — breaks convention
  last_name: String      // snake_case — breaks camelCase
}
type Mutation {
  CreateUser(...): User  // noun, not verb — reads like a query
  Remove(id: ID!): Bool  // vague; no input wrapper
}
camelCase + past-tense — Preferred schema.gql 
# ✓ Consistent: camelCase fields, past-tense mutations
type User {
  firstName: String
  lastName: String
  emailAddress: String
}
type Mutation {
  createUser(input: CreateUserInput!): UserPayload!
  updateUser(id: ID!, input: UpdateUserInput!): UserPayload!
  deleteUser(id: ID!): DeletePayload!
}
3
GraphQL — Performance
Avoid deeply nested queries — use DataLoader

Nesting more than 3–4 levels causes N+1 resolver problems and poor performance. Use DataLoader for batch loading of related entities.

Deep nesting — Avoid query.graphql 
# ❌ N+1: each level fires a new DB query
query {
  users {
    orders {
      items {
        product {
          category {
            vendor {
              warehouses { ... }
            }
          }
        }
      }
    }
  }
}
-- 7 levels deep. Each level = N queries.
-- 100 users × 3 orders × 5 items = 1500 queries.
DataLoader batch — Preferred schema.gql 
# ✓ DataLoader batches and caches foreign keys
const userOrdersLoader = new DataLoader(ids =>
   db.orders.where('user_id').in(ids).then(rows =>
    rows.groupBy('user_id').map(userId => rowsForUser)
  )
);

// Query depth: max 3 levels, use references for more
query {
  users {
    orders {
      product { category { id name } }
    }
  }
}
// Batching: 4 queries instead of 1500.
✓ DataLoader automatically batches multiple requests for the same entity into a single database query — use it for any foreign-key relationship in your schema.
4
GraphQL — Mutations
Always use input types for mutations

Don't use inline arguments in mutations. Define input types — they compose, version, and document better than flattened argument lists. They also make it easier to add fields without breaking existing callers.

Inline args — Avoid schema.gql 
# ❌ Inline arguments — hard to extend, no composition
type Mutation {
  createUser(
    name: String!
    email: String!
    age: Int
    role: String
    // Adding 'address' here breaks existing callers
  ): UserPayload!
}
Input type — Preferred schema.gql 
# ✓ Input type — extensible, composable, self-documenting
input CreateUserInput {
  name: String!
  email: String!
  age: Int
  role: UserRole
  address: AddressInput  // additive — no breaking change
}
type Mutation {
  createUser(input: CreateUserInput!): UserPayload!
}
Versioning

API Evolution

1
Versioning — Strategy
Version in the URL path

Most consumers expect the version in the URL. It's explicit, bookmarkable, and easy to route. The simplest and most widely understood convention.

Header versioning — Avoid requests.http 
# ❌ Version in header — invisible, unbookmarkable
GET /users
API-Version: 2   // Consumer must read docs to know this
Accept: application/vnd.api+json; version=2
-- Cannot bookmark or share the URL.
-- Harder to route at the gateway level.
Path versioning — Preferred requests.http 
# ✓ Version in path — visible, bookmarkable, routable
GET /v1/users   // explicit
GET /v2/users   // upgrade path is clear
DELETE /v1/users/42
-- Any stakeholder can see the version in the URL.
-- Gateways, load balancers, and consumers all benefit.
2
Versioning — Rules
Never make breaking changes in a published version

If you must break, increment the version. Only add additive, non-breaking changes to a live version: new optional fields, new endpoints, new enum values.

✗ Removing a field, changing a type, or renaming an endpoint are all breaking changes. They break existing clients without warning if they're in the same version.
New optional field → non-breaking Remove field → breaking Change type → breaking Rename endpoint → breaking
3
Versioning — Lifecycle
Sunset old versions gracefully

Announce deprecations in responses. Use the Deprecation header or a deprecated field in the schema. Give consumers time — minimum 6 months before removal.

No warning — Avoid response.json 
# ❌ Version removed without notice
HTTP/1.1 404 Not Found
{
  "error": "v1 is no longer supported"
}
-- Consumer had no time to migrate.
-- Broken production integrations.
Graceful deprecation — Preferred response.json 
# ✓ Deprecation header + sunset date announced
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Jan 2026 00:00:00 GMT
Deprecation-Reason: "Use /v2/users instead"
{
  "data": [...],
  "deprecated": true,
  "sunsetDate": "2026-01-01",
  "migrationGuide": "/docs/v2/migration"
}
Error Handling

Predictable Error Responses

1
Errors — Shape
Use a consistent error envelope

Every error response should follow the same shape: a machine-readable code, a human-readable message, and optional details for field-level validation errors.

Inconsistent shapes — Avoid response.json 
# ❌ Each endpoint returns a different error shape
{ "error": "User not found" }           // endpoint A
{ "message": "Invalid input", "code": 400 } // endpoint B
{ "err": "validation_failed" }         // endpoint C
-- Consumers can't write generic error handlers.
Uniform envelope — Preferred response.json 
# ✓ Every response — success or error — follows the same shape
{
  "code": "USER_NOT_FOUND",
  "message": "No user found with ID 42",
  "requestId": "req_7f3a2b9c",
  "details": [
    { "field": "id", "issue": "does not exist" }
  ]
}
2
Errors — Status Codes
Use accurate HTTP status codes

The status code is the first signal a consumer receives. Don't return 200 for errors. Don't return 500 for client mistakes. The code must be accurate.

200 for errors — Avoid response.json 
# ❌ Status 200 with an error body — misleading
HTTP/1.1 200 OK
{
  "success": false,
  "error": "validation_failed"
}
-- Monitoring, proxies, and clients all see "OK".
-- Error handling is buried in the body.
Accurate codes — Preferred response.json 
# ✓ Status code matches the error type
HTTP/1.1 400 Bad Request
{
  "code": "VALIDATION_FAILED",
  "message": "email must be a valid address"
}
---
HTTP/1.1 404 Not Found
{
  "code": "USER_NOT_FOUND",
  "message": "No user with ID 42"
}
3
Errors — Security
Never expose stack traces in production

Internal errors (500s) should log full details server-side and return a generic message to clients. You control what the consumer sees — always.

Stack trace exposed — Avoid response.json 
# ❌ Production error with stack trace
HTTP/1.1 500 Internal Server Error
{
  "error": "Unhandled exception",
  "stack": "NullReferenceException: Object reference...",
  "query": "SELECT * FROM users WHERE id = ?"
}
-- Exposes DB schema, library versions, internal paths.
-- Attackers use this for reconnaissance.
Generic error — Preferred response.json 
# ✓ Internal error logged; consumer sees generic message
HTTP/1.1 500 Internal Server Error
{
  "code": "INTERNAL_ERROR",
  "message": "An unexpected error occurred. Reference: req_7f3a2b9c",
  "requestId": "req_7f3a2b9c"
}
-- Full details logged server-side with requestId.
-- Consumer can't infer internal implementation.
Pagination

Cursor & Offset Patterns

1
Pagination — Type
Prefer cursor-based pagination for large or live datasets

Cursors are stable across insertions — page N+1 won't include items that appeared between page loads. Essential for infinite feeds, real-time data, and any frequently updated dataset.

Offset pagination — Avoid GET /users?page=3&limit=20 
# ❌ Offset pagination — unstable on live data
GET /users?page=2&limit=20

-- User 15 deletes their account.
-- Page 2 now has only 19 items.
-- A new user signs up and appears on page 3.
-- Items shift between page loads — consumer confusion.
Cursor pagination — Preferred GET /users?after=cursor_abc&first=20 
# ✓ Cursor — stable across insertions
GET /users?after=cursor_abc&first=20
-- cursor_abc encodes the position after the last item.
-- New insertions before the cursor are invisible.
-- Consumer sees consistent page contents.

# Response envelope
{
  "data": [...],
  "pageInfo": {
    "hasNextPage": true,
    "endCursor": "cursor_def"
  }
}
2
Pagination — Use Case
Use offset pagination only for bounded, admin-style lists

Offset pagination is appropriate for admin UIs, dropdown searches, or any scenario where jumping to a specific page is a legitimate consumer need. If the dataset is large or frequently updated, use cursors.

3
Pagination — Metadata
Always include total count and hasNextPage

Paginated responses must include total (or totalCount) and hasNextPage so consumers can render UI elements like page numbers, "Load more" buttons, and progress indicators correctly.

No metadata — Avoid response.json 
# ❌ Response has no count — consumer can't render UI
{
  "data": [...],
  "users": [...]  // inconsistent key names too
}
-- How many total results exist?
-- Is there a next page?
Rich metadata — Preferred response.json 
# ✓ Predictable envelope with total and pagination state
{
  "data": [...],
  "total": 3847,
  "limit": 20,
  "hasNextPage": true,
  "hasPreviousPage": false,
  "startCursor": "cursor_aaa",
  "endCursor": "cursor_abc"
}
-- Consumer can render: "Showing 1-20 of 3847"
-- "Load more" button knows when to hide.
Auth

Authentication Patterns

1
Auth — Transport
Use Bearer tokens, never put them in URLs

The standard HTTP auth header. Keep tokens out of URL query strings — they leak via server logs, browser history, CDN caches, and browser bookmarks.

Token in URL — Avoid requests.http 
# ❌ Token in query string — exposed everywhere
GET /users?token=eyJhbGciOiJIUzI1NiJ9...
-- Appears in Apache/Nginx access logs.
-- Appears in browser history.
-- Appears in CDN cache keys.
-- Appears in browser bookmarks if shared.
Bearer header — Preferred requests.http 
# ✓ Token in Authorization header — not in URLs
GET /users
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
-- Not stored in URL logs by default.
-- Not present in browser history.
-- Automatically excluded from CDN cache keys.
2
Auth — Codes
Distinguish 401 (unauthenticated) from 403 (unauthorised)

401 means no valid credentials were provided. 403 means valid credentials were provided but the identity lacks permission. Conflating them makes debugging hard for consumers.

Conflated — Avoid response.json 
# ❌ Both cases return 403 — ambiguous
HTTP/1.1 403 Forbidden
{ "error": "Access denied" }
-- Consumer can't tell: no credentials, or insufficient?
-- Forces re-authentication when it's a permission problem.
Distinct codes — Preferred response.json 
# ✓ Clear distinction with actionable error codes
-- No credentials:
HTTP/1.1 401 Unauthorized
{ "code": "MISSING_TOKEN", "message": "Provide a Bearer token" }

-- Valid credentials, insufficient permission:
HTTP/1.1 403 Forbidden
{ "code": "INSUFFICIENT_PERMISSION", "message": "Role 'viewer' cannot delete users" }
3
Auth — Approach
Never roll your own auth — use established standards

OAuth 2.0, OpenID Connect, and JWT are battle-tested protocols. If you're hand-rolling a session mechanism, you're almost certainly missing edge cases that lead to authentication bypasses.

✗ Home-grown auth is the most common source of critical vulnerabilities. Token forging, timing attacks, insecure session storage, and missing rotation are all things that libraries solve for you.
